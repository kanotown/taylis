# 添削・レビュー依頼 (L9、M63〜M64)

ROADMAP の L9 (LAB.md §F)。学生が原稿 (添付や Overleaf のリンク) を載せたメッセージに「レビュー依頼」を付け、依頼先 (教員) と
希望日を決める。メッセージの下に状態 (依頼中 / 対応中 / 完了) が出て、依頼先は自分宛ての依頼を一覧で整理できる。修論・学会の
締切前に教員へ 10 人分の依頼が集まるときに効く。

**状態**: 設計 (2026-10-02)。§7 の「決めてほしいこと」の返事を待っている。

## 1. 方針: タスク (M55) の上に作る

LAB.md の設計時は専用の表 `review_requests` を想定していたが、その後にできたタスク (M55、TASKS.md) が必要なものの大半を
すでに持っている。

| レビュー依頼に要るもの | タスクにあるか |
|---|---|
| メッセージから作る | ある (`source_message_id`、メニューの「タスクにする」) |
| 依頼先 (複数可) と割り当ての通知 | ある (担当者、`kind = task` のプッシュ) |
| 希望日と当日の通知 | ある (`due_on`、期限の日 8:00 に担当者へ) |
| 状態 (依頼中 / 対応中 / 完了) | ある (`todo` / `doing` / `done`) |
| 自分宛ての一覧 | ある (「自分のタスク」の「自分の担当」) |
| **DM での依頼** (学生 → 教員の DM) | **無い**: DM のメッセージから作ると個人用になり、相手に見えない |
| **メッセージの下の状態** | **無い**: タスクは元のメッセージを指すが、メッセージ側には何も出ない |
| **自分が出した依頼の一覧** | **無い** |

そこで、別の仕組みは作らず、**メッセージに付いたタスク**を 3 か所広げる。レビュー依頼は「依頼先を担当者にしたタスク」で、
画面の言葉だけ変える。研究室以外の「この投稿の対応をお願い」にもそのまま使える。

## 2. 変えること

### 2.1 DM でもメッセージのタスクを共有する

- DM・グループ DM のメッセージから作るタスクに、**担当者として DM のメンバーを付けられる**ようにする。担当者がいるタスクは
  その DM のメンバー全員に見える (`tasks.channel_id = DM`)。担当者がいなければ今までどおり個人用。
- DM にはボード (「タスク」タブ) は作らない (TASKS.md §2 のまま)。DM のタスクが出るのは、メッセージの下 (§2.2)、「自分の
  タスク」(担当・依頼)、カレンダー。
- 権限は共有のタスクと同じ (DM のメンバーが見る・直す。消すのは作った人・担当者・管理者)。

### 2.2 メッセージの下に状態を出す

- `MessageOut.tasks: [{id, kind, status, assignee_ids, due_on, owner_id}]` (そのメッセージから作られ、消されていないタスク。多くても
  数件)。無いときは空の配列。
- タスクの作成・状態・担当・期限の変更・削除で、元のメッセージの `updated_seq` を進め、`message.updated (change = "tasks")`
  を出す (回収 `collection` と同じ流れ、SYNC_PROTOCOL §6)。これで切断中の変化も差分 (§7.3) で届く。題名・メモだけの変更では
  出さない (メッセージの下には出ないため)。
- 端末はメッセージの下に 1 行のチップを出す: 「レビュー依頼 · 加納 · 依頼中 · 10/9 まで」(完了は「完了」で灰色、期限を過ぎた
  未完了は赤)。押すとタスクの詳細。依頼先なら詳細に「対応を始める」「完了にする」の大きなボタン。
- チップの言葉は種類で分ける (§7 の 3): `tasks.kind = review` は「レビュー依頼」、`task` (「タスクにする」で作ったもの) は「タスク」。

### 2.3 依頼の入口と一覧

- メッセージのメニューに「**レビューを依頼**」(「タスクにする」の隣)。作成フォームは「タスクにする」と同じで、題名は
  「レビュー: <本文の抜粋>」、担当者 (依頼先) の選択を先に出し、期限の欄は「希望日」。チャンネルでも DM でも使える。
- 「自分のタスク」に「**自分が依頼した**」を足す: 自分が作り、自分以外が担当のタスク (完了は最近 50 件)。
  `GET /tasks/mine` に `requested` を足す (今の `personal` / `assigned` と並べる)。
- 依頼先の側は今の「自分の担当」で足りる。並びは期限の近い順 (期限なしは後ろ)。

## 3. API の変更 (`/api/v1`)

- `POST /tasks` / `PATCH /tasks/{id}`: DM のメッセージからのタスクで `assignee_ids` を受け付ける (DM のメンバーに限る。
  それ以外は `400 task_invalid_assignee`)。
- `MessageOut.tasks` (§2.2)、`message.updated` の `change = "tasks"`。
- `GET /tasks/mine` の応答に `requested: TaskOut[]`。
- 新しい表は無し。移行 0056 で `tasks.kind` (`task` / `review`、既定 `task`。`POST /tasks` で指定、`TaskOut.kind`) と、
  `MessageOut.tasks` のための索引 `(source_message_id) WHERE deleted_at IS NULL` を足す。`tasks.channel_id` に DM が入るように
  なる。

## 4. 通知

- 依頼先へ: 既存の割り当ての通知 (「〇〇 がタスクを割り当てました」) を、`kind = review` では「〇〇 がレビューを依頼しました:
  題名」にする。
- 依頼した人へ (`kind = review` だけ): 依頼先が**完了にしたとき**だけ「〇〇 がレビューを完了しました: 題名」(新しい通知。
  「対応中」では出さない)。
  プッシュの設定は「タスク」のオン/オフに従う。
- 希望日の通知は既存の期限の通知 (当日 8:00、担当者へ) のまま。
