# WORKSPACES

複数のワークスペースを登録して切り替える仕組み (Slack のワークスペース切り替え、Mattermost デスクトップの
複数サーバーに相当)。

## 1. 方針

- **1 デプロイ = 1 ワークスペース** (ARCHITECTURE.md D12) は変えない。ワークスペースを増やすとは、
  別の ChikuwaChat サーバーを立てることを意味する。
- クライアントが複数のサーバーを登録して切り替える。サーバー同士は互いを知らない。
  共有チャンネル、ワークスペース横断の検索、アカウントの統合はしない。
- サーバー側の追加は 3 つだけ: 認証不要の `GET /api/v1/server`、未読サマリー `GET /api/v1/sync/summary`、
  プッシュのペイロードの `workspace_id`。同期プロトコル (SYNC_PROTOCOL.md) はワークスペースごとに
  そのまま動く。

## 2. 用語

| 用語 | 意味 |
| --- | --- |
| ワークスペース | クライアントに登録した (サーバー URL, アカウント) の組。1 サーバーにつき 1 アカウント |
| アクティブなワークスペース | 画面に表示しているワークスペース。常に 1 つ |
| workspace_id | サーバーのデプロイを識別する UUID (§3)。クライアントが決める値ではない |

## 3. サーバー

### 3.1 `GET /api/v1/server` (認証不要)

```json
{ "product": "chikuwachat", "workspace_id": "0192…", "name": "開発チーム", "api_version": "0.1.0" }
```

- `product` は常に `"chikuwachat"`。ワークスペース追加の画面で、入力された URL が ChikuwaChat の
  サーバーかどうかを確かめるのに使う。
- `workspace_id` は `workspace_identity` テーブルの 1 行 (DATA_MODEL.md)。migration 0034 で作られ、
  バックアップ / 復元で保たれる。行が失われていた場合は起動時に新しい値で作り直す
  (クライアントは次に `GET /server` を読んだ時に新しい値を覚える)。
- `name` は環境変数 `WORKSPACE_NAME`。空なら `APP_NAME` (既定 `taylis`)。切り替え UI の表示名。
- 返すのはログイン画面でも見える程度の情報 (名前と API バージョン) だけ。

### 3.2 `GET /api/v1/sync/summary`

```json
{ "badge": 3, "has_unread": true }
```

開いていないワークスペースのバッジのための軽い要約 (bootstrap を丸ごと取らない)。規則はクライアントの
アプリアイコンのバッジ (M13f) と同じ:

- `badge`: 所属し、アーカイブされていない会話について、DM / グループ DM は未読数、チャンネルは
  メンション数、ミュート中 (レベル `none` または `muted_until` が未来) はメンション数を足したもの。
- `has_unread`: 未読がある会話 (ミュート中はメンションがある場合のみ) かフォロー中スレッドの未読があれば true。

### 3.3 プッシュ

ペイロード (PUSH_NOTIFICATIONS.md §5) に `workspace_id` を入れる。APNs は `aps` の外、FCM は `data`
に入る。クライアントは通知のタップをこの値でワークスペースに振り分ける (§7)。

## 4. クライアントが保存するもの

| 項目 | 保存先 | 内容 |
| --- | --- | --- |
| ワークスペース一覧 | 設定 (desktop: localStorage、iOS: UserDefaults、Android: SharedPreferences) | 下の表の項目。秘密は含めない |
| アクティブなワークスペース | 同上 | サーバー URL |
| refresh token | 資格情報ストア (desktop: Keychain / Credential Manager、iOS: Keychain、Android: Keystore で暗号化) | アカウント名 = `サーバー URL|ユーザー名` (従来と同じ) |
| ローカルストア | SQLite | ファイル名はサーバー URL とユーザー名のハッシュ (SYNC_PROTOCOL.md §11、従来と同じ) |

ワークスペース一覧の 1 件:

| 項目 | 説明 |
| --- | --- |
| `server_url` | 正規化した URL (スキーム + ホスト (+ ポート) + パス、末尾の `/` なし)。一覧のキー |
| `workspace_id` | `GET /server` の値。プッシュの振り分けと重複登録の検出に使う |
| `name` | `GET /server` の値。起動時とワークスペースを開いた時に読み直す |
| `username` / `user_id` | サインインしているアカウント |
| `badge` / `has_unread` | 最後に知った未読 (§6)。開いていないワークスペースの表示用 |

既存のインストール (1 サーバーだけを覚えている) は、初回起動時に保存済みのサーバー URL と
ユーザー名から 1 件のワークスペースを作って移行する。名前は `GET /server` が読めるまでホスト名で表示する。
iOS / Android は保存済みの refresh token があるときだけ移行する (無ければ従来どおりのログイン画面)。

## 5. 追加・切り替え・削除

### 5.1 追加

1. サーバー URL を入力する (スキームが無ければ `https://` を補う)。
2. `GET /server` を読む。`product` が違う / JSON でない → 「taylis のサーバーではありません」。
   ネットワークエラーは共通の文言 (errors.json の network)。
3. `workspace_id` が登録済みのワークスペースと同じなら追加せず、そのワークスペースに切り替える
   (同じサーバーに別の URL で入り直すのを防ぐ。1 サーバーにつき 1 アカウント)。
4. ログイン (ユーザー名、パスワード、必要なら 2 段階認証) に成功したら一覧に加え、アクティブにする。
   キャンセルすると元のワークスペースに戻る。

### 5.2 切り替え

- アクティブなワークスペースを変えると、画面はそのワークスペースのストアを表示する。開いていた
  チャンネル、スクロール位置、下書きはワークスペースごとのストアに残る。
- 切り替え先のセッションは SYNC_PROTOCOL.md §7.2 の手順で始める (保存済みの refresh token から)。
  refresh が `401` ならそのワークスペースだけログイン画面にする (他は影響を受けない)。
- desktop (Tauri) はキーボードで切り替えられる: `⌘` / `Ctrl` + `1`〜`9` で一覧の n 番目 (Slack と同じ)。

### 5.3 サインアウト / 削除

ワークスペースのメニューの「サインアウト」は SYNC_PROTOCOL.md §11 の手順 (セッション失効、
ローカルストアと refresh token の削除、そのワークスペースの通知を消す) を行い、一覧から外す。
アクティブなワークスペースだった場合は、サインイン済みの最初のワークスペースに切り替える (無ければ一覧の
先頭のログイン画面、一覧が空ならログイン画面)。

## 6. 開いていないワークスペース

| | desktop (Tauri) | iOS / Android |
| --- | --- | --- |
| 接続 | サインイン済みの全ワークスペースが WS と同期を続ける (Slack と同じ)。画面に出すのはアクティブな 1 つ | アクティブな 1 つだけが接続する。他はプッシュで知る |
| 通知 | 全ワークスペースのデスクトップ通知を出し、2 つ以上あるときはタイトルにワークスペース名を付ける (Tauri の通知はクリックを受け取れないので、切り替えはレールから) | 各サーバーがこの端末にプッシュを送る (ログイン時にそれぞれ端末を登録済み) |
| バッジ | 各ワークスペースのストアから計算 (アクティブと同じ規則) | `GET /sync/summary` をフォアグラウンド復帰時と切り替え UI を開いた時に読む。プッシュ受信で `has_unread` を立てる |
| アプリアイコンのバッジ | 全ワークスペースの合計 | iOS: アクティブの値 + 他のワークスペースの最後に知った `badge` の合計。サーバーが APNs で付ける値はそのサーバーの分だけなので近似 (PUSH_NOTIFICATIONS.md §4.2)。Android はランチャーの数字バッジを出さない (通知の件数が目印) |

desktop で全ワークスペースを接続し続けるのは、デスクトップにはプッシュが無く、接続を切ると他の
ワークスペースのメンションに気づけないため。数個のワークスペースなら WS 数本とストア数個で足りる。

モバイルでは、開いていないワークスペースのサーバーから見るとユーザーは接続していないので、
プッシュが通常どおり届く (PUSH_NOTIFICATIONS.md §4.1 の「操作中なら送らない」に当たらない)。

## 7. 通知のタップ

1. ペイロードの `workspace_id` から登録済みのワークスペースを探す。
   見つからない (古いサーバーで `workspace_id` が無い / 復元で値が変わった) 場合は、各ワークスペースの
   ローカルストアに `channel_id` のチャンネルがあるものを探し、それも無ければアクティブなワークスペースで開く。
2. アクティブでなければ切り替える (§5.2)。
3. 従来どおり同期してからチャンネル / スレッドを開く (SYNC_PROTOCOL.md §11)。

フォアグラウンドで受けた通知の表示 (iOS の `willPresent`、Android の通知生成):

- アクティブなワークスペースで開いている会話の通知は出さない (WS で受け取り済み)。
- アクティブなワークスペースの他の会話: WS のメッセージからアプリ自身が通知を出すクライアント (Android) は
  それで足りるのでプッシュは出さない (二重になる)。出さないクライアント (iOS) はプッシュのバナーを出す。
  どちらもサーバは操作中の利用者にはふつうプッシュを送らない (PUSH_NOTIFICATIONS.md §4.1)。
- 他のワークスペースのプッシュは、その WS が無いので常に出す。
ワークスペースが 2 つ以上あるとき、Android は通知のサブテキストにワークスペース名を入れる
(iOS はサーバーが作る表示なので付かない。将来 Notification Service Extension で付けられる)。

## 8. プッシュトークンの更新

APNs / FCM のトークンが変わったら、サインイン済みの **全ワークスペース** に `PUT /devices/current`
を送る (開いていないワークスペースも、保存済みの refresh token で access token を取り直して送る)。
refresh はワークスペースごとに 1 つの API クライアントが直列に行う (同時に 2 本の refresh を送ると
再利用検知でセッションが失効するため。SECURITY.md §2)。

## 9. Web クライアント

ブラウザ版はページと同じオリジンのサーバーにだけ接続する (Cookie セッション、M12j)。
ワークスペースの切り替え UI は出さない。別のワークスペースはそのサーバーの URL をブラウザで開く。

## 10. やらないこと

- ワークスペースをまたぐ検索、未読一覧、DM。
- 1 サーバーに複数アカウントでの同時サインイン。
- 一覧の並べ替え (追加順)。必要になったら加える。
