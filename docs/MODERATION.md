# MODERATION

アカウントの削除、メッセージの報告、ユーザーのブロック (M104)。App Store の審査ガイドライン 1.2 (ユーザー生成コンテンツ:
報告の手段、ブロック、運営者による対応) と 5.1.1(v) (アプリ内からのアカウント削除)、Google Play のアカウント削除の
ポリシー (アプリ内の手段と、ウェブ上の削除の案内 URL) と UGC のポリシーに応えるための最小限の仕組み。数十人の招待制の
ワークスペースに合わせ、単純さを優先する。

## 1. まとめ

| 機能 | どこから | 何が起きるか |
| --- | --- | --- |
| アカウントを削除 | 4 クライアントの「設定 → アカウント → アカウントを削除」、公開ページ `/account-deletion` (案内) | パスワード (Google のアカウントはユーザー名) で確認、**すぐに**匿名化。メッセージは「退会したユーザー」として残る |
| 管理者による削除 (匿名化) | Desktop / Web の「管理 → ユーザー」の ⋯ →「削除 (匿名化)…」(有効な人にも、無効化した人にも) | 本人の削除と同じ処理 |
| メッセージを報告 | 4 クライアントのメッセージの操作 →「報告する」 | 理由と補足を保存、本文の写しを取り、管理者全員にモデレーションのボットから DM。管理者は「管理 → 報告」で確認し「対応済み」にする |
| ブロック | 4 クライアントのプロフィール →「ブロック」/「ブロックを解除」、「設定 → アカウント」の一覧で解除 | 相手のメッセージは自分の画面で折りたたまれ、相手からの通知・プッシュは来ず、相手は自分に 1 対 1 の DM を送れない。相手には知らされない |

## 2. アカウントの削除

### 2.1 本人の削除

- `POST /api/v1/users/me/delete-account` `{password}` または `{confirm_username}` → `204`。
  - パスワードのあるアカウントはパスワードで確認する (違えば `422 invalid_password`。401 にしないのは、クライアントが認証済み
    リクエストの 401 でセッションを捨てるため。SECURITY.md §2.7)。
  - パスワードの無いアカウント (Google でログインして作られた人、SSO.md) は自分のユーザー名を打ち直す (大文字小文字は無視。
    違えば `422 invalid_confirmation`)。Google に再認証させる仕組みは作らない (ログイン中の端末を持っていることと
    名前の打ち直しで十分とした)。
  - パスワード変更が必要な状態 (`must_change_password`) でも呼べる (仮パスワードで確認する)。
  - パスワードの総当たりはログインと同じアカウントごとのレートリミットで抑える (`login_account`、既定 5 回 / 分)。
- **最後の管理者は削除できない**: 本人が admin で、ほかに有効な admin (無効化されていない、role = admin) がいなければ
  `409 last_admin`。先にほかの人を管理者にする。ボットのアカウントは対象外。
  有効な管理者を減らす操作 (本人のアカウント削除、管理者による無効化・admin 以外への変更・匿名化、
  年度更新のゲスト化) は、トランザクション単位の 1 つの排他 (`pg_advisory_xact_lock(hashtext('admin_set'))`) で
  1 つずつ行い、その中で残る管理者を数え直す。排他は User 行や名簿 (`lab_roster`) のロックより先に取る。
  最後の二人が同時に退会しても、退会と無効化・降格が競っても、後の方が `409 last_admin` になり、
  有効な管理者が必ず 1 人残る (レビュー v0.1.37 #1)。
- 処理は管理者の匿名化 (M10、`admin.anonymize_in_tx`) と同じで、**同じトランザクションですぐに**行う:
  - 全セッションを失効 (`revoke_reason = anonymized`、開いている WS は `session.revoked` で切れる)。端末のプッシュトークンを消して無効にする。
  - ユーザー名を `deleted-<id の先頭 12 桁>` (誰も名乗れない予約の形、SECURITY.md §2.9)、表示名を「退会したユーザー」に。
  - メールアドレス・肩書・ステータス・通知キーワード・おやすみモードとおやすみ時間・プロフィール画像 (オブジェクトも
    コミット後に消す) を消す。パスワードは誰も知らない乱数のハッシュに。2 要素認証、Google の結び付け (`user_identities`) と
    未使用のチケット、名簿の行 (研究テーマを含む)、本人のブロックの一覧 (`user_blocks` の blocker 側) を消す。
  - `deactivated_at` を付け、`user.deactivated` を全員へ (各端末の名簿の表示が「退会したユーザー」になる)。
  - 監査 `user.account_deleted` (actor = 本人、target = その id。名前は残さない)。
- コミットの後、有効な管理者全員 (本人以外) に、モデレーションのボット (§5) から DM で知らせる:
  「メンバーが自分でアカウントを削除しました (現在の表示: 退会したユーザー / @deleted-…)」。元の名前は書かない
  (消した個人情報を管理者の DM に複製しない)。誰だったかは監査ログの id で追える。
- クライアントは成功したらそのワークスペースからサインアウトする (端末のデータを消す。SYNC_PROTOCOL.md §11)。

### 2.2 猶予期間を設けない理由

削除の要求から実際の削除までの猶予 (取り消し期間) は作らない。データを消すのは匿名化だけで、行そのものは残る
(メッセージの帰属のため) ので、猶予の間の状態 (ログインできるのか、表示はどうするのか) と、それを進めるジョブを持つほどの
利点が無い。誤操作はパスワードの再入力と確認の画面で防ぐ。取り消したい場合は、管理者が新しいアカウントを作る。

### 2.3 残すもの (プライバシーポリシーに書くこと)

- チャンネル・DM に投稿したメッセージ・添付ファイル・リアクション・キャンバスの版・タスクなど、**ほかの人と共有している
  会話の記録**は残し、投稿者は「退会したユーザー」(`deleted-…`) と表示する。会話の流れ (返信・引用・スレッド) が
  途中で欠けると、残った人の記録として意味を失うため。Slack・Mattermost の退会と同じ扱い。
- App Store の 5.1.1(v) は、サービスの提供や法令上の理由で保持が必要なデータを残すことを、それを利用者に説明していれば
  認めている。プライバシーポリシーには次を書く: 「アカウントを削除すると、プロフィール (名前・ユーザー名・メールアドレス・
  画像・ステータス)・ログイン情報・端末とプッシュ通知の登録はすぐに消去されます。共有した会話に投稿したメッセージと
  ファイルは、ほかの参加者の記録として残り、投稿者は『退会したユーザー』と表示されます。消したいメッセージは削除の前に
  ご自身で削除するか、管理者に依頼してください。」
- 監査ログには名前を含まない識別子だけが残る。バックアップ (SECURITY.md §9) には削除前の状態が保持期間の間残る。
- 本人が過去に報告した記録 (`message_reports.reporter_id`) は id のまま残る (表示は「退会したユーザー」)。

### 2.4 公開の案内ページ (Google Play の「アカウント削除の URL」)

- `GET /account-deletion` (認証なし、静的な HTML、`server/app/core/templates/account_deletion.html`)。Caddy はこのパスを
  アプリへ渡す (ほかの不明なパスは Web クライアントを返すため、`infra/Caddyfile` に `handle /account-deletion`)。
- 内容: アプリ / Web 版での削除の手順 (設定 → アカウント → アカウントを削除)、Web 版を開くリンク (`/`)、ログインできない
  ときは管理者に依頼すること、消えるもの・残るもの (§2.3)。日本語と短い英語。
- ストアに登録する URL は `https://<サーバ>/account-deletion`。

### 2.5 管理者による削除

- 「管理 → ユーザー」の ⋯ →「削除 (匿名化)…」(M10 の `POST /admin/users/{id}/anonymize` を使う)。有効な人にも出す
  (以前は無効化した人にだけ)。自分自身・ボット・匿名化済みの人には出さない (サーバも自分は `409 cannot_modify_self`)。
- 監査は `admin.user_anonymized` (actor = 管理者)。CLI `anonymize-user` も同じ。

## 3. メッセージの報告

- `POST /api/v1/messages/{id}/report` `{reason, note?}` → `201` (2 回目以降は最初の報告を `200` で返す。同じ人が同じ
  メッセージを報告できるのは 1 回)。
  - `reason`: `spam` (迷惑・スパム) / `harassment` (嫌がらせ) / `inappropriate` (不適切な内容) / `other` (その他)。
    `note` は 1,000 文字まで。
  - 報告できるのは、そのメッセージを読める人 (メンバー、参加前のプレビューができる公開チャンネル) で、自分のメッセージは
    不可 (`400 cannot_report_own`)。削除済みは `404`。
  - 応答は自分の報告の `{id, message_id, reason, created_at}` だけ。ほかの人の報告や件数は返さない。
  - レートリミット: 1 人 10 件まで続けて、その後 1 分に 1 件 (`429`)。
  - 保存 (`message_reports`、DATA_MODEL.md): チャンネル、報告者、投稿者、理由、補足、**本文の写し** (4,000 文字まで。投稿者が
    後から編集・削除しても、管理者が何が報告されたかを確かめられるように)、状態 (`open` / `resolved`)。監査
    `moderation.message_reported`。
- 管理者への通知: コミットの後、モデレーションのボット (§5) から有効な管理者全員 (報告した本人を除く) に DM:
  「🚩 メッセージが報告されました / 理由 / 投稿者 / 場所 (#チャンネル、DM ならダイレクトメッセージ) / 補足 / メッセージの
  リンク (`<サーバ>/m/<id>`) / 「管理」→「報告」で確認」。補足と名前は `<` と `*` を全角にしてメンションや装飾にならない
  ようにする。DM はふつうのメッセージなので、管理者の端末にプッシュが届く。本文の写しは DM に載せない (不快な内容を
  通知に広げない。管理画面で見る)。
- 管理者の画面 (Desktop / Web の「管理 → 報告」): `GET /admin/reports?status=open|resolved|all` (新しい順、200 件)。
  理由・日時・場所・投稿者・報告者・本文の写し (後で削除されたかどうかも)・補足。「対応済みにする」
  (`POST /admin/reports/{id}/resolve`) /「未対応に戻す」(`/reopen`)、監査 `moderation.report_resolved` / `_reopened`。
  対応そのもの (メッセージの削除、無効化、匿名化) は既存の管理操作で行う。管理者がメンバーでない非公開の会話の
  メッセージでも、報告の写しで内容を確かめられる (報告した人が管理者に見せることを選んだもの)。
- 通知の DM は送れなくても (ボットが無効、DM の作成に失敗) 報告そのものは残り、管理画面に出る (ログに残す)。

## 4. ブロック

- `PUT /api/v1/users/{id}/block` (新しく付けたら `201`、既にあれば `200`)、`DELETE /api/v1/users/{id}/block`、
  `GET /api/v1/users/me/blocks`。自分自身は `400 cannot_block_self`、見えない人 (guest から見た範囲外) と存在しない人は
  `404`。レートリミット 30 回 / 分。
- 本人だけのもの (`user_blocks`): 端末間は `block.updated` (audience = 本人、`{user_id, blocked}`) で揃え、bootstrap の
  `blocked_user_ids` に入る。**ブロックされた人には何も届かない** (イベントも一覧も)。
- 効果:
  - **表示**: チャンネル・グループ DM・スレッドで、ブロックした人のメッセージは「ブロック中のユーザーのメッセージ」の
    1 行に折りたたまれ、「表示」でその行だけ開く (開いたのはアプリを閉じるまで。端末に保存しない)。クライアント側の
    表示の規則で、サーバは履歴や同期からメッセージを外さない (未読数・既読位置の規則 §10 を変えないため)。
  - **1 対 1 の DM**: ブロックされた人は、ブロックした人への新しい DM を開けず (`POST /dms` が `403 dm_unavailable`)、
    既にある 1 対 1 の DM にも投稿できない (`POST /channels/{id}/messages` が `403 dm_unavailable`)。文言は「この
    ユーザーにはメッセージを送れません」で、理由 (ブロック) は言わない。ブロックした側は送れる (返事は来ない)。
    グループ DM は拒まない (ほかの人との会話を壊さない。自分の画面で折りたたむだけ)。
  - **通知**: ブロックした人のメッセージ・メンション・スレッドの返信・リアクション・キャンバスのメンションでは、
    プッシュ (PUSH_NOTIFICATIONS.md) も、開いているアプリの通知も出さない。アクティビティの一覧 (メンション・返信・
    リアクション) とその未読数からも外す。
  - 共有のチャンネルには両方とも残る (チャンネルから外れたりはしない)。
- 残る差 (受け入れたもの): 会話ごとの未読数・メンション数のバッジは、ブロックした人のメッセージも数える (サーバの
  未読の数え方は人を区別しない。§10 の共有規則を変えない)。ブロックされた人は、DM の拒否から推測はできる。

## 5. モデレーションのボット

- 管理者への通知 (§2.1、§3) を送る bot アカウント (`system_bots` の key `moderation`、表示名「モデレーション」)。
  最初に必要になったときに作る (締切のボット M85 と同じ作り)。管理者が無効化すると通知は止まる (報告は管理画面に残る)。
- メンションを取らない投稿 (`mentions=False`) で、各管理者との 1 対 1 の DM に送る。同じ通知の再送は `client_msg_id`
  (uuid5) で 1 回にまとまる。
