## 計画の全文: 大量メッセージ時の性能、研究室向けの機能、Canvas、スマホ UI

## 0. 要点

- **大量メッセージで重くなるか**: チャンネルの総件数が増えても、サーバはほとんど遅くなりません。34 万件のチャンネルでも、履歴 1 ページは最新でも 3 年前でも約 10 ms でした。
- **遅くなるのは次の 2 つです。**
  1. **検索**: 今の時点で 1.4〜6.0 秒かかります。原因は SQL の 1 か所で、書き換えると 1〜85 ms になることを確かめました。
  2. **端末が読み込んで持ち続けるメッセージの件数**: 上限がないので、使い続けるほど増えます。
     - いちばん重いのは iOS です。100 件でも、新着 1 件の処理に約 0.34 秒、1,000 件で 1.0〜2.5 秒かかります。
     - Desktop は再起動すると 1 チャンネル 500 件まで読み戻すので、1 文字打つたびに 150〜230 ms かかります。
     - 原因は特定済みで、小さな修正を重ねれば大半はなくなります。
- **動作の誤りが 2 つ見つかりました。最初に直します。**
  - Android でスレッドが既読にならない。チャンネルを開いたときや検索結果から飛んだとき、目的の位置に移動しない。v0.1.1 から含まれています。
  - 未読が 50 件を超えるチャンネルを初めて開くと、見ていない未読まで既読になり、その状態が全端末に同期される。Android で確認しました。Desktop / Web もコード上は同じ作りです。
- **進める順番**: 正しさと性能 (M17〜M21) → 研究室の基本とスマホの会話画面 (M22〜M27) → スマホの画面構成 (M28〜M31) → Canvas (M32〜M37) → 研究室の拡張とスマホの仕上げ (M38〜)。
- **v0.1.2 のタグ**: そのまま出して構いません。今回の不具合はすべて v0.1.1 以前からあるもので、リリースの仕組みは Android を作りません。Android のアプリは M17 の修正後に入れ直してください。

工数の目安: S = 1 日程度、M = 数日、L = 1〜2 週、XL = それ以上。

## 1. 膨大なメッセージがあってもチャンネルは重くならないか

### 測定の条件

- 使ったデータベースは `chikuwa_perf` です。46.5 万件、3 年分、31 人で、教員・D・M・B4 の構成にしました。
- #big (34 万件) は負荷試験用のチャンネルです。普通の研究室のチャンネルは 3 年で 4,400〜5,000 件 (1 日 5〜7 件) にしました。
- 測定中は他の作業が並行していて、負荷平均が 34〜39 (10 コア) でした。絶対値は悲観的に読んでください。
- iOS はシミュレータ、Android は M1 の JVM とエミュレータで測りました。実機では測っていません。
- スクリプトと生データは `/tmp/scratch` にあります。リポジトリは変更していません。

### 大事な見方

重さを決めるのは「チャンネルに何件あるか」ではなく、「端末が何件を読み込んで持っているか」です。

- チャンネルを開いたときに読むのは最新の 50 件だけです。
- しかし保持件数を減らす仕組みがありません。次のものがすべて積み上がります。
  - 上へ戻って読んだ過去ログ
  - リアルタイムで届く新着
  - 再接続時に取り戻す差分 (最大 5,000 件)
- 件数を減らすのは Desktop の起動時 (500 件まで) だけです。iOS と Android は一度も減らしません。

### サーバ

**総件数が増えても遅くならないもの**

| 処理 | 測定値 |
|---|---|
| 履歴 1 ページ (最新 / 15 万件前 / 3 年前) | 10.0 / 9.8 / 10.6 ms。どの深さでも索引を 9 バッファ読むだけ |
| 差分同期 | 200 件で約 15 ms。2,890 件遅れからの追いつきで約 200 ms |
| 投稿 | #big で 22 ms、小さな DM で 16 ms (件数の影響なし)。再送 (冪等) は 6 ms |
| 500 返信のスレッド | 20 ms |
| WebSocket | 500 接続でも、最後の端末に届くまで 100 ms 未満。1 接続あたり約 7 µs / 5 KB |
| 起動時の同期 (bootstrap) | 85 ms。1 プロセスで毎秒約 31 回まで処理でき、再起動後に 150 台が一斉に再接続しても約 5 秒でさばける |

**データが増えると遅くなるもの** (深刻度はレビュー後の評価)

| # | 内容 | 深刻度 | 今の値 | 修正後 |
|---|---|---|---|---|
| S1 | 語を含む検索で PGroonga の索引が使われない。本文の条件とファイル名の条件を OR でつないでいるのが原因 (search/repository.py:78-85)。関連度の点数が常に 0 なので、「関連度順」が実は「新しい順」になっている | 高 | 1.4〜6.0 s。0 件ヒットでも 2.8 s。数百万件では 15〜60 s の見込み | 1〜85 ms で、点数も正しく付く |
| S2 | DB 接続が既定の 15 本だけ。遅い検索が 16 本同時に走ると、他のすべての処理が待たされる | 中 | 履歴 17 ms → 6.4 s | S1 を直せば起きなくなる。上限時間などの保険も追加する |
| S4 | 語なしの絞り込み (日付、from:、has:) で表を全部読む | 中 | 95〜196 ms。280 万件では 0.3〜0.7 s | 2 ms 未満 |
| S3 | /mentions で表を全部読む | 低 | 70〜84 ms | 17.7 ms |
| S5 | 未読数をチャンネルごとに 1 本ずつ数えている | 低 | 普段は約 10 ms。29 万件ためた場合だけ 113 ms | — |
| S6 | フォロワーの多いスレッドへの返信 (31 人) | 低 | 107 ms、SQL 143 本 | SQL 約 5 本 |
| S8 | GET /files の並べ替えに使える索引がない | 低 | 添付 2 万件で 146 ms | 0.5 ms |

### Web / Desktop

- **問題なく速いところ**
  - ログイン後、79 ms でメイン画面が出ます。
  - #big を開くと 120 ms で表示されます。
  - Markdown の解析は CPU の約 1% です。
- **遅くなる仕組み**
  - ストアが 1 回変わるたびに、読み込み済みの全行を描き直します (W2, 高)。
  - 「1 回の変化」に当たるもの: 1 文字の入力、どのチャンネルかを問わない「入力中」表示、新着、リアクション、リンクプレビューの応答、スクロール中の既読の 1 歩。

| 読み込み済みの行数 | 1 回の変化で描き直す時間 | JS ヒープ |
|---|---|---|
| 50 (DM) | 22 ms | — |
| 100 (#big を開いた直後) | 36 ms | 28.6 MB |
| 約 600 | 235 ms | 137 MB |
| 約 2,600 | 991 ms | 570 MB |
| 約 5,100 | 1.76 s | 1.11 GB |

- **ブラウザ版**は最初 50〜100 行なので軽いです。**Desktop 版 (Tauri)** は再起動後、よく使うチャンネルが 500 行前後で始まるので、1 打鍵 150〜230 ms の遅れが日常的に出ます。遅い Windows ノートではこの 2〜3 倍と見込みます。
- **リンクプレビュー (W3, 高)**
  - 応答 1 件ごとに画面全体を描き直します。
  - 再起動後に 500 行のチャンネルを開くと、約 83 件の応答で合計約 15 秒カクつきます。
  - 60 件を超えた分はレート制限 (429) で失敗し、そのプレビューは再起動まで表示されません。
- **未読を読み進めるスクロール (W4, 高)**: 350 行で 1 フレームの中央値が 117 ms、1,150 行で 367 ms です。
- **行が重い (W1 / W5, 中)**
  - 仮想化がなく、1 行あたり DOM が 62 ノード、メモリが約 215 KB あります。
  - 62 ノードのうち 42 は、隠れているホバー時の操作バーです。
- **修正の効果 (確認済み)**: MessageRow をメモ化すると、5,000 行でも 1 回の変化が 2.7 ms で済みます。

### iOS (いちばん重い)

| 保持している件数 | 新着 1 件の処理 | スクロール 1 フレーム | 他のチャンネルの未読が変わったとき |
|---|---|---|---|
| 50 | — | — | 69 ms |
| 100 | 341 ms | 59 ms | — |
| 300 | 353 ms | 約 155 ms | 314 ms |
| 1,000 | 1.0〜2.5 s | 196〜503 ms | 約 1.0 s |
| 10,000 | 9.8 s | 4.7 s | 10 s |

チャンネルを開くと、1,000 件で CPU 5.5 秒、1 万件で 57 秒と +517 MB でした。

**原因** (いずれも重なって効いています。IOS-7 以外は深刻度「高」)

| # | 内容 |
|---|---|
| IOS-1 | 画面より上にある行も、再描画のたびに全部作り直している |
| IOS-2 | スクロールの 1 フレームごとに状態を書き込み、画面全体を作り直している |
| IOS-3 | 日付を解析するたびにフォーマッタを新しく作る (1 回 156 µs。共有すれば 0.67 µs) |
| IOS-4 | `Store.messages()` (全件の絞り込みと並べ替え) を、再描画 1 回で 7〜15 回呼んでいる |
| IOS-5 | 1 件挿入するたびに、そのチャンネルの辞書全体をコピーしている |
| IOS-6 | 保持件数に上限がない。起動時に全件をメインスレッドで読む (5 万件で 561 ms) |
| IOS-7 (中) | 別のチャンネルの変化でも、開いている画面を再描画する |

- **件数の増え方**: 一度開いたチャンネルは、その後の新着をすべて持ち続けます。活発なチャンネルなら数か月で 1,000 件、1〜2 年で 1〜2 万件になります。
- **修正の効果 (試作で確認済み)**
  - 2,000 件で新着 1 件が 2.4 s → 411 ms。
  - 1,000 件で行の再計算を止めると、スクロールが 503 → 23 ms、他のチャンネルの変化が 984 → 30 ms。
  - 挿入はその場で更新すれば、件数に関係なく 0.002 ms。
- **問題なく速いところ**: スレッド画面です。500 返信で開くのに約 380 ms、スクロールは 1 フレーム 3〜5 ms でした。
- **補足**: Xcode の Run で入れた Debug ビルドは、アプリ自身のループが 7〜12 倍遅くなります (IOS-11, 低)。

### Android

- **問題なく速いところ**
  - 同期の処理: 2,340 件の追いつきが CPU 8〜10 ms、新着 1 件が 1 ms 未満です。
  - タイムラインを組み立て直すのは、そのチャンネルの行が変わったときだけです。1,000 件で 1 ms、1 万件で 5.8 ms (M1 の JVM。実機は 3〜6 倍遅いと見込み)。
  - 1 文字の入力や「入力中」表示では組み立て直しません。当初は「組み立て直す」と指摘されていましたが (AND-1)、レビューで否定されました。
- **起動時に全件を読む (AND-4, 高)**
  - 5 万件で、エミュレータ上 2.7〜4.2 秒スピナーのままでした。
  - 10 万件では OOM になり、`Store.load` の `runCatching` がそれを握りつぶして、未送信メッセージ (outbox) と下書きまで捨てます。
- **保持件数に上限がない (AND-2, 中)**
  - 研究室の利用者なら 1〜3 年で 3.5〜10 万件、メモリにして 35〜100 MB になります。
  - 起動時はその約 2 倍が一時的に必要です。

### 全端末の正しさの問題

- **AND-3 (高, Android)**
  - 行のキーを `client_msg_id` に変えたとき (19779b3, v0.1.1)、検索する側の 2 か所が id のまま残りました。
  - その結果、実際の返信 500 件のうち 0 件が一致し、スレッドの既読 API が一度も呼ばれません。
  - チャンネルを開いたとき、検索結果やパーマリンクから飛んだときも、目的の位置ではなく常に最新の位置へ移動します。
- **AND-5 (中) と Desktop / Web の同じ作り**
  - 未読が 50 件を超えるチャンネルを、手元に同期済みの履歴がない状態で開いたときに起きます。Web はローカルに保存しないので、ページを読み込み直すたびにこの状態です。
  - 最新 50 件だけを読み、区切り線をその先頭に置き、見えている行まで既読にします。
  - #big (未読 2,007 件) では、既読位置が見ていない約 1,950 件を飛び越え、全端末で未読が約 40 件になりました。
  - これは SYNC_PROTOCOL §10 (画面に出た行だけを既読にする) に反します。
  - Desktop は Timeline.tsx:46-51, 107-117 と engine.ts の catchUp を読んで同じ作りだと確認しました。iOS もレビューで同じ作りと指摘されています。

## 2. 研究室向けの調整 (times を含む)

**方針**

- 研究室専用のものは新しい `lab` モジュールに閉じ込めます。
- 身分・学年は表示とグループ分けにだけ使い、権限には使いません。ロールは今の admin / member / guest のままです。
- 学籍番号・成績・出欠は保存しません。
- times、テンプレート、定期投稿、締切は、研究室以外でも使える汎用機能として作ります。

**今の機能でできること**

- ユーザーグループ (@m1 など)
- 投稿制限チャンネル
- 重要度と「確認しました」
- 個人のリマインダー、1 回だけの予約送信
- 投票
- 招待リンク
- ゲスト

**足りないもの**

1. 構造化された身分と学年
2. 「誰の times か」を示すデータ
3. 繰り返しの仕組み
4. チャンネル全体に向けた締切

### 推奨する機能と順番

| 順 | 機能 | 中身 | 工数 |
|---|---|---|---|
| 1 | 名簿と学年グループ (L1) | 身分・学年・指導教員・研究テーマ。名簿順の表示。`@b4 @m1 @m2 @d @faculty @students @alumni` を自動で保つ「管理グループ」 | M |
| 2 | times (L2) | サイドバーに「Times」節。作成は冪等。他人の times は**静かな未読**にする: 太字にせず、メンションのときだけバッジとプッシュ。指導教員は自動でフォローする | M |
| 3 | テンプレートと /日程 (L3) | `/日報` `/週報` で雛形を挿入し、`{date}` などを置き換える。`/日程` は日付を選択肢にした投票を作る | S |
| 4 | 確認の拡張と教員の権限 (L4) | 未確認の人の一覧、本人にだけ届く催促、チャンネルのオーナーを追加する機能、非公開 → 公開の変換をメンバーの admin に限る、在席表示を本人が隠せる | M |

- Times フィードは、チャンネルごとに LATERAL で上位 50 件を取ってから混ぜる形で書きます。0.95 ms で済みます。素直に `IN + ORDER BY` で書くと 43 ms かかり、履歴に比例して遅くなります。

## 3. Canvas (Slack Canvas に相当する機能)

### 推奨する MVP

- **置き場所**: キャンバスは必ずいずれかの会話 (チャンネル / DM / グループ DM / 自分との DM) に属します。
  - 閲覧・編集・検索・画像・通知の権限は、既存のチャンネルのメンバーシップでそのまま決まります。新しい ACL は作りません。
  - 研究計画は、学生と教員の DM か非公開チャンネルに置けば非公開のまま保てます。
- **画面**
  - 会話の見出しに「メッセージ | キャンバス」タブを付けます。
  - 議事録などの他のキャンバスは、会話の一覧とサイドバーの「キャンバス」に並べます。
- **本文**: Markdown です。メッセージの記法に、チェックリスト、`![](attachment:id)` の画像、区切り線を足します。
- **保存**
  - 入力が 2 秒止まるたびに、元にした版 (`base_rev_id`) と冪等キーを付けて本文全体を `PUT` します。
  - その間に他の人が保存していれば、**サーバが 3-way マージ**します。まず行単位で、同じ行が重なったときは語句単位で比べます。
  - 同じ語句を別々に書き換えたときだけ、「自分の版 / 相手の版 / 両方残す」を選んでもらいます。
  - マージのコードはサーバ (Python) の 1 か所だけです。3 端末はマージのコードを持たずに済みます。
- **その他の機能**
  - 履歴: 版の比較・復元・名前付きの版
  - テンプレート: 週報 / 議事録 / 研究計画 / 学会準備 / 卒論・修論スケジュール
  - PGroonga による検索
  - コメントは、作成時に会話へ投稿する共有メッセージのスレッドで受けます

### 測定 (合成したキャンバス 5,000 件、4,725 万字)

| 項目 | 結果 |
|---|---|
| 検索 (`ARRAY[title, body]` の索引 1 つ) | 1.8〜12 ms |
| 検索を `title OR body` の形で書いた場合 | **1,374 ms**。この形は使わない (S1 と同じ落とし穴) |
| 保存 1 回のトランザクション | 約 1 万字で 3.8 ms、約 8 万字で 18 ms |
| マージの試作 | 別の行を 2 人が編集した 300 回、同じ行の別の位置を編集した 200 回が、どちらもすべて競合なし。10 万字で 30 ms |
| 1 行の中を文字単位でマージ | 2 万字で 3 s と遅すぎる。語句単位にすると 9 ms |

### 採らない案とその理由

- **ブロック型**: 3 端末それぞれにブロックエディタを作る費用が大きすぎます。
- **CRDT (Yjs / Automerge)**: Swift / Kotlin / Python のバインディングがどれも 1.0 前です。モバイルは WebView に頼ることになり、ネイティブ UI の方針から外れます。

### 拡張の順番

1. Phase 2: 保存時に増えたメンションの通知、チェック項目の担当と期限、「自分のタスク」一覧、「○○さんが編集中」の表示。
2. 保存とマージで足りないと分かった場合だけ、Desktop / Web をリアルタイム共同編集にします。CodeMirror 6 + Yjs で、サーバは pycrdt から本文を導出します。モバイルは今の `PUT` のまま使えます。
3. 必要なら Desktop だけ WYSIWYG (TipTap) にします。
4. RAG 用に `canvas_embeddings` を足します。

**性能の注意**: モバイルで描画するときは、本文の解析と日付の計算を保存時に 1 回だけ行います。iOS の IOS-3 / IOS-4 と同じ問題を繰り返さないためです。検索は EXPLAIN で索引が使われていることをテストで確かめます。

## 4. スマホ UI を Slack に近づける

### 今の主な差

- **長押しメニューが 3 端末でばらばら**
  - iOS: contextMenu に最大 16 行が並ぶ
  - Android: 行に付くドロップダウン。「テキストをコピー」がない
  - Web: ラベルのないアイコンが 13 個
- **Android の会話の見出し**: アイコンが 7 個並び、360dp の幅だと題名が隠れます。
- **iOS の会話画面**: スレッドがシートで開きます。過去ログはボタンを押して読み込みます。
- **画面の構成**
  - 下部のタブがありません。
  - DM 一覧に最後の発言のプレビューがありません。
  - 設定はシートやダイアログ 1 枚に詰め込まれています。

## 6. 実装の前に決めてほしいこと

**D1. 進める順番**

- 選択肢:
  - A) 正しさと性能 → 研究室の基本と会話画面 → スマホの画面構成 → Canvas → 拡張 (§5 の順)
  - B) Canvas を研究室の基本より前に
  - C) スマホの画面構成を先に
- 推奨: A。
  - M17 は実害のある不具合の修正です。M18〜M20 は小さな修正で効果が大きいものです。
  - times の置き場所はスマホ UI の設計と関わるので、研究室の基本を先にします。

**D2. 端末が持つ履歴の件数**

- 選択肢: 1 チャンネル 500 件 / 1,000 件 / 上限なし (今のまま)
- 推奨: 500 件。
  - Desktop は再起動時にすでに 500 件にしています。
  - 遡るときの 1 ページは約 10 ms でサーバから取り直せます。
  - オフラインで読めるのは各チャンネルの最新 500 件になります。

**D3. times の未読と書き込み**

- 選択肢: 静かな未読 (メンションのときだけ通知) / 普通のチャンネルと同じ / ミュートと同じ
- 推奨: 静かな未読で、誰でも書き込めるようにし、本人が「スレッドだけ」に切り替えられるようにします。

**D4. 週報・進捗報告をどこに書くか**

- 選択肢:
  - A) #週報 に研究室 bot が毎週スレッドを立て、日報は times に書く
  - B) 各自の times に書く
  - C) 学生ごとの Canvas (週報テンプレート) に書く
  - D) 指導チャンネル (本人と指導教員の非公開チャンネル) に書く
- 推奨: A。
  - 提出状況が見えて、本人にだけ催促できるのは A だけです。
  - Canvas は研究計画・議事録・研究室のしおりに使います。

**D5. admin を誰が持つか、プライバシーをどう守るか**

- 選択肢: 教授が admin / 技術担当 (職員や D の学生) が admin / 今のまま
- 推奨: 誰が admin でも、次の 3 点を行います。
  - 非公開 → 公開の変換を、そのチャンネルのメンバーである admin に限る。
  - 在席表示を本人が隠せるようにする。
  - 運用者 (サーバ・DB・バックアップに触れる人) には技術的にすべて読めることを明記する。

  admin を誰にするかは研究室の文化で選んでください。

**D6. Canvas の編集方式**

- 選択肢:
  - A) 自動保存 + サーバ側マージ + Markdown とツールバー
  - B) 「保存」ボタンを押す wiki 型
  - C) 最初から Yjs でリアルタイム共同編集 (Desktop だけ)
- 推奨: A。
  - 3 端末ともネイティブのまま作れます。
  - 試作では 500 回のマージがすべて競合なしでした。
  - WYSIWYG は学生が使いにくいと分かってから Desktop だけに足します。

**D7. スマホの下部タブ**

- 選択肢: 4 つ (ホーム / DM / アクティビティ / 自分) / 3 つ (Slack の 2024 年以降と同じ) / 5 つ (検索もタブにする)
- 推奨: 4 つにし、スマホ幅だけに適用します。iPad・タブレット・広いブラウザは今のサイドバー型のままです。

**D8. iOS の最低バージョン**

- 選択肢: iOS 18 に上げる / 17 のまま
- 推奨: 研究室の全員の iPhone が 18 以上なら上げます。
  - 入力欄の書式ボタン (選択範囲の API) を UIKit のラッパーなしで作れます。
  - M19 の iOS 18 向けの分岐も要らなくなります。
