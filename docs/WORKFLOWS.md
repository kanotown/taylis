# ワークフロー (M94 / M95)

Slack の「ワークフロー」のように、決まった形の投稿をフォームから手軽に出す機能。利用者の要望 (2026-10-04):
「Slackのワークフローのような機能を実装できる？ 学部ゼミ・院ゼミの案内を出したり、ゼミ欠席報告や書誌情報報告が手軽に
できるようにしたい」。

**状態**: M94 (サーバと Desktop / Web) は実装済み (2026-10-04、移行 0075)。M95 (iOS / Android) は §8 の仕様で後から作る。

## 1. 問題

研究室の Slack では次のワークフローを使っていた。

- 「ゼミ欠席報告」: #報告-ゼミ欠席 に
  `*【報告者】* <@U…>  *【報告の内容】* ゼミの欠席  *【日付】* 2026-07-28 …` を投稿。
- 「学部ゼミ案内」: #2026ゼミ に `<!channel> *【第 6 回学部ゼミのお知らせ】* • *日時*：2026年5月19日 13:00 JST • …` を投稿。
- #報告-書誌情報 に書誌情報 (著者・題名・会議名 …) を報告。

M30 の投稿テンプレートは入力欄に文を入れるだけなので、日付の書式・報告者のメンション・選択肢 (欠席 / 遅刻 / 早退) を
毎回手で直すことになり、書式も人によって崩れる。必要なのは「項目を埋めると、決まった形の投稿が決まったチャンネルに出る」こと。

## 2. 決めたこと

| # | 決めたこと | 推奨 (採用) | ほかの案 (採らなかった理由) |
|---|---|---|---|
| D1 | 誰として投稿するか | **出した本人として** ふつうのメッセージの経路 (`create_message`) で投稿する。メンション・通知・未読・プッシュ・投稿制限・検索・編集・削除がすべてそのまま効き、誰の報告かが一目で分かる | ワークフローごとのボット (Slack と同じ)。報告者が本文のメンションでしか分からず、ボットをチャンネルに入れる配線 (RECURRING と同じ) が要り、投稿制限も素通りする |
| D2 | 本文の作り方 | 管理者が書く **Markdown の雛形** に `{{項目のキー}}` を置き、**サーバが**値で置き換える (クライアントの描き分けを信じない)。クライアントのプレビューは同じ規則 (`apps/shared/workflows.json` の検証ベクタ) で描く | クライアントが本文を作って送る (改ざんでき、3 端末で書式がずれる) |
| D3 | 入力値の扱い | 人が打った値 (短文・長文・選択肢) の中のメンションの構文 `<@` `<!` は全角の `＜` にして無効にする。メンションになるのは「人」の項目 (`<@id>`) と、雛形に管理者が書いた `<!channel>` などだけ | 値をそのまま入れる (誰でも `<!channel>` を差し込める)、値の Markdown も消す (報告に箇条書きが書けなくなる) |
| D4 | 記録の置き場所 | 投稿したメッセージそのものが記録。`messages.workflow_id` と `workflow_name` (投稿した時の名前) を持ち、`MessageOut.workflow = {id, name}` で返す。提出の表は作らない | 提出 (値) を別の表に保存する (集計は「後で」§9 に。いま要るのは投稿だけ) |
| D5 | 項目の種類 | 短文・長文・日付・時刻・日時・選択・人・チェック の 8 種類。既定値は 固定値・今日・自分・今日以降で最初の N 曜日 の 4 種類だけ | 数値・ファイル・複数選択の選択肢・条件分岐 (今は要らない。足すときは種類を増やすだけ) |
| D6 | 管理する人 | 管理者 (送り先を読めること) と送り先チャンネルのオーナー。ゲストは不可。作成・変更・削除は監査に残す | 誰でも作れる (投稿の形を勝手に増やせてしまう) |
| D7 | 名前 | ワークスペースで重複不可 (大文字小文字を区別しない、消したものを除く)。`/名前` で開けるように、空白を含まない名前を勧める (含む名前は `/wf 名前` かメニューから) | チャンネルごとに重複可 (`/名前` が曖昧になる) |
| D8 | 定期的な催促 (「⚡ 〇〇 を入力してください」) | **M94 では作らない** (§9)。作るときの形も §9 に書いた | M94 に入れる (投稿にボタンを付ける新しい形・ボットの配線・端末の処理が要り、M94 が倍になる) |

## 3. データ (移行 0075)

`workflows`

| 列 | 意味 |
|---|---|
| id, created_by, created_at, updated_at, deleted_at | 論理削除 (投稿の `workflow_id` が残るため) |
| name (1〜40) | 表示名と `/名前`。前後の空白を除き、連続する空白は 1 つ。消していないものの中で `lower(name)` が一意 (部分索引) |
| emoji (NULL 可) | メニューに出す絵文字 (Unicode か `:shortcode:`)。NULL なら ⚡ |
| description (0〜200) | メニューとフォームの説明 |
| channel_id | **送り先**のチャンネル (公開・非公開。DM は不可) |
| offered_channel_ids uuid[] | メニューに出すチャンネル (送り先は必ず含む。最大 10) |
| fields jsonb | 項目の配列 (§3.1)。最大 20 |
| template text (1〜4000) | 本文の雛形 (§3.2) |
| enabled | 止めている間は一覧に出るが実行できない (`409 workflow_disabled`) |

`messages` に 2 列を足す: `workflow_id uuid NULL REFERENCES workflows(id)`、`workflow_name varchar(40) NULL`。

### 3.1 項目 (`fields` の 1 つ)

```json
{"key": "日付", "label": "日付", "type": "date", "required": true, "help": "", "default": {"kind": "today"}}
```

| 項目 | 規則 |
|---|---|
| key | 1〜30 文字の文字 (どの文字体系も)・数字・`_` (NFC)。雛形の `{{key}}`。項目の中で一意 |
| label | 1〜40 文字。フォームの見出し |
| type | `text` (短文、1 行・200 文字まで) / `textarea` (長文、4000 文字まで) / `date` (`YYYY-MM-DD`) / `time` (`HH:MM`) / `datetime` (`YYYY-MM-DDTHH:MM`、端末の壁時計の時刻をそのまま。タイムゾーンは持たない) / `select` (選択肢から 1 つ) / `user` (人。`multiple` で複数、20 人まで) / `checkbox` (はい / いいえ) |
| required | 必須。チェックの必須は「オンにすること」(同意の確認など) |
| help | 0〜200 文字。欄の下の説明 |
| options | `select` だけ: 1〜30 個、各 1〜80 文字、重複不可 |
| multiple | `user` だけ |
| default | NULL か `{"kind": "literal", "value": …}` (短文・長文・選択 (選択肢のどれか)・日付・時刻・日時は文字列、チェックは真偽値) / `{"kind": "today"}` (日付・日時。日時は `time` も付けられる、無ければ 09:00) / `{"kind": "next_weekday", "weekday": 0〜6, "time"?: "HH:MM"}` (日付・日時。**今日を含めて**最初のその曜日、0 = 月曜) / `{"kind": "me"}` (人) |

既定値は**フォームを開いた端末が**その端末の日付で埋める (サーバは送られた値だけを見る)。

### 3.2 雛形と描き方 (サーバが正、検証ベクタ `apps/shared/workflows.json`)

- `{{key}}` (中の前後の空白は可) を値で置き換える。1 回だけ置き換え、結果は読み直さない (値に `{{…}}` があってもそのまま)。
  保存の時に、雛形のすべての `{{…}}` が項目のキーであることを確かめる (`400 workflow_template_invalid`、`details.unknown`)。
- 値の書き方:
  - 短文・長文・選択: 打った文字のまま。ただし `<@` `<!` の `<` は `＜` に (D3)。改行は長文だけ (短文の改行は空白に)。
  - 日付 `2026年7月28日 (火)`、時刻 `13:00`、日時 `2026年5月19日 (火) 13:00`。
  - 人: `<@id>` を空白で区切って並べる (ふつうのメンションになり、その人に通知が届く)。
  - チェック: `はい` / `いいえ`。
- **空の行を落とす**: `{{…}}` を含む行で、その行の `{{…}}` がすべて空 (任意の項目が未入力) なら、その行ごと出さない
  (「*【理由】* 」だけの行が残らない)。`{{…}}` の無い行はそのまま。
- 結果の前後の空白行を落とす。空になったら `400 workflow_values_invalid`。20,000 文字を超えても同じ。
- 雛形に管理者が書いた `<!channel>` `<!here>` `<@id>` `<@group:id>` はそのまま本文に入り、ふつうに効く。
  `@channel` を書ける人に制限は無く (投稿制限のあるチャンネルではそもそもオーナー・管理者しか投稿できない)、雛形を
  書くのは送り先のオーナー・管理者なので、保存の時の追加の検査は無い。エディタは「このワークフローは @channel で全員に
  通知します」と出す。

### 3.3 値の検査 (`POST /workflows/{id}/submit` の `values`)

キーごとの値。種類に合わない値・知らないキー・必須の空 (空文字・空配列・未送信、必須のチェックがオフ)・長すぎる値・
選択肢に無い値・存在しない / 無効化された / ボットの人は `400 workflow_values_invalid`、`details.fields = {key: 理由}`
(理由: `required` `invalid` `too_long` `not_an_option` `user_not_found`)。

## 4. API (`/api/v1`)

| 呼び出し | 誰が | 内容 |
|---|---|---|
| `GET /workflow-templates` | ログインした人 | 「テンプレートから作成」の雛形 (§6)。`WorkflowTemplateOut[]` = `{key, name, emoji, description, fields, template}` |
| `GET /workflows` | ログインした人 | **自分が管理できる**ワークフロー (管理画面の一覧)、名前の順。止めたものも |
| `GET /channels/{id}/workflows` | そのチャンネルを読める人 | そのチャンネルに出すワークフローのうち、送り先を読めるもの (メニューと `/` の候補)、名前の順。止めたものも (`enabled`) |
| `GET /workflows/{id}` | 送り先を読める人 | 1 件 |
| `POST /workflows` | 管理できる人 | `{name, emoji?, description?, channel_id, offered_channel_ids?, fields, template, enabled?}` → 201 |
| `PATCH /workflows/{id}` | 管理できる人 | 同じ項目の一部。送り先を変えるときは新しい送り先も管理できること |
| `DELETE /workflows/{id}` | 管理できる人 | 論理削除 → 204。投稿は残り、ラベルは投稿した時の名前のまま |
| `POST /workflows/{id}/submit` | 送り先に投稿できる人 | `{client_msg_id, values}` → `MessageOut` (新しく作れば 201、同じ `client_msg_id` の再送なら 200 で同じメッセージ) |

`WorkflowOut` = `{id, name, emoji, description, channel_id, offered_channel_ids, fields, template, enabled, created_by,
created_at, updated_at, can_manage, can_run, run_blocked}`。`run_blocked` は自分が実行できない理由
(`disabled` / `archived` / `not_a_member` / `posting_restricted`、実行できるなら null。ゲストもメンバーなら実行できる)。メニューは理由を添えて
灰色にする。一覧の変更はイベントを出さない (定期投稿と同じく、メニューを開くたび・`/` を打つたびに読む。端末は 1 分だけ覚える)。

送信は投稿の速度制限 (1 分あたりの投稿数) を同じく数える。

エラー: `404 workflow_not_found` (無い・消した・送り先を読めない)、`403 workflow_manage_restricted`、
`400 workflow_channel_unsupported` (送り先・出す先が DM)、`409 channel_archived` (送り先がアーカイブ済みの作成・変更・送信)、
`409 workflow_name_taken`、`400 workflow_name_reserved` (`/help` など組み込みのコマンドと `wf`)、
`400 workflow_template_invalid`、`400 workflow_values_invalid`、`409 workflow_disabled`、`409 too_many_workflows`
(ワークスペースで 200 件まで)、`403 not_a_member` / `403 posting_restricted` (送信、ふつうの投稿と同じ)、
出す先のチャンネルが無い・読めない → `404 channel_not_found`。項目の定義の形の誤りは `422 validation_error`。

`MessageOut.workflow`: `{id, name}` か null。古いクライアントはこの欄を知らず、ふつうの投稿として出す (iOS の Codable と
Android の `ignoreUnknownKeys` は知らない欄を無視する。確認済み)。

## 5. 権限

- **管理** (作成・変更・止める・削除): 送り先チャンネルのオーナー (メンバーで role = owner)、または送り先を読める管理者
  (メンバー、または公開チャンネル)。ゲストは管理しない。出す先に足せるのは、自分がメンバーのチャンネル (管理者は読めるチャンネル)。
- **見る**: 送り先を読める人 (公開チャンネルなら参加していない人も。その人には `run_blocked = not_a_member`)。
- **実行**: 送り先のメンバーで、そこに投稿できる人 (投稿制限 `owners` のチャンネルではオーナーと管理者)。ふつうの投稿と同じ
  検査を `create_message` がそのまま行う。ワークフローを出しているチャンネル (メニューを開いた場所) は問わない。
- 監査: `workflow.created` / `workflow.updated` (変えた項目) / `workflow.deleted`。送信は監査しない (メッセージが記録)。

## 6. テンプレートから作成 (サーバの固定の一覧、ワークフローとしては作らない)

| テンプレート | 項目 | 雛形 (要約) |
|---|---|---|
| 学部ゼミ案内 | 回 (短文・必須)、日時 (日時・必須・次の火曜 13:00)、場所/URL (短文)、内容 (長文)、発表者 (人・複数) | `<!channel> *【第 {{回}} 回学部ゼミのお知らせ】*` と `• *日時*：…` の行 |
| 院ゼミ案内 | 同じ | `<!channel> *【第 {{回}} 回院ゼミのお知らせ】*` … |
| ゼミ欠席報告 | 報告者 (人・必須・自分)、日付 (日付・必須・今日)、内容 (選択: 欠席 / 遅刻 / 早退、必須、欠席)、理由 (長文) | `*【報告者】* {{報告者}}` `*【報告の内容】* ゼミの{{内容}}` `*【日付】* {{日付}}` `*【理由】* {{理由}}` |
| 書誌情報報告 | 著者・タイトル・会議/雑誌名・年 (必須)、巻号ページ、DOI/URL、種類 (選択: 国際会議 / 国内会議 / 論文誌 / 研究会 / その他、必須) | `*【書誌情報】* {{種類}}` と `• *著者*：…` の行 |

選ぶとエディタに名前・項目・雛形が入り、送り先を選んで保存する。定義は `server/app/modules/workflows/templates.py`。

## 7. 画面 (Desktop / Web、M94)

- **実行**: 入力欄の「＋」→「⚡ ワークフロー…」と、チャンネルのヘッダーの ⋯ →「ワークフロー…」で、そのチャンネルに出す
  ワークフローの一覧 (絵文字・名前・説明・送り先が別なら「→ #送り先」、実行できなければ理由)。選ぶとフォーム。
  `/名前` (組み込みのコマンド・テンプレートの名前が先) と `/wf 名前` でも開く。`/` の候補にも「⚡ /名前」で出す。
  スレッドの入力欄には出さない (投稿は送り先のトップレベル)。
- **フォーム**: 項目を並べ、既定値を端末の日付で埋める。必須・長さ・選択肢をその場で確かめ (サーバも同じ検査)、
  下に投稿のプレビュー (§3.2 の規則)。「投稿」で `client_msg_id` を 1 つ作り、失敗して押し直しても同じキーで送る
  (二重投稿しない)。成功したら閉じ、送り先が別のチャンネルなら「#送り先 に投稿しました」と知らせる。
  サーバの `workflow_values_invalid` の `details.fields` は欄ごとに出す。
- **投稿の印**: `workflow` のあるメッセージの上に小さく「⚡ 名前」(押すと `GET /workflows/{id}` を読んでフォームを開く。
  消された・実行できないものはその理由をトーストで知らせる)。消したメッセージには出さない。
- **狭い画面**: チャンネル詳細の「ワークフロー」から同じダイアログ (使う / 管理)。
- **管理**: 管理 →「ワークフロー」のタブ (管理者) と、チャンネルの ⋯ →「ワークフロー…」の「管理」(オーナー・管理者)。
  一覧 (名前・送り先・項目の数・停止中)、作成 / 編集のダイアログ: 名前・絵文字・説明・送り先・出す先 (追加のチャンネル)、
  項目のエディタ (追加・上下の並べ替え・削除、種類ごとの設定、既定値)、雛形 (「項目を挿入」のボタンで `{{キー}}` を入れる) と
  その場のプレビュー (既定値と例の値で描く)、「テンプレートから作成」、止める / 再開、削除 (確認あり)。

## 8. スマホの仕様 (M95、iOS / Android)

サーバは M94 のまま (追加の API は無い)。

1. **投稿の印**: `MessageOut.workflow` を読む (iOS: `CodingKeys` に足し、無くても読めること。Android: JSON に足すだけ、Room の
   版は上げない)。メッセージの上に小さく「⚡ 名前」。押すとフォーム (実行できない・消されたなら何もしない)。
2. **一覧**: 会話の入力欄の「＋」(添付のメニュー) に「ワークフロー」、チャンネル詳細に「ワークフロー」。
   `GET /channels/{id}/workflows` を開くたびに読む (1 分覚えてよい)。`run_blocked` があれば灰色にして理由
   (`not_a_member`: 「#送り先 に参加すると使えます」、`posting_restricted`: 「#送り先 はオーナーと管理者だけが投稿できます」、
   `disabled`: 「停止中」、`archived`: 「#送り先 はアーカイブ済みです」。文は Desktop の `runBlockedText` と同じ)。
3. **`/` のコマンド**: Desktop と同じ順 (組み込み → テンプレート → ワークフロー)。`/wf 名前` も。
4. **フォーム** (全画面のシート): 種類ごとの標準の部品 (短文 `TextField` / 長文 複数行 / 日付・時刻・日時は標準のピッカー /
   選択は Picker・ドロップダウン / 人は既存のメンバー選択 (複数可) / チェックは Toggle・Switch)。既定値は端末の日付
   (今日・今日以降で最初の N 曜日・自分)。必須の印と help。下にプレビュー (`apps/shared/workflows.json` のベクタを
   単体テストで通すこと)。送信は `client_msg_id` を 1 つ作ってフォームが閉じるまで使い回す。`workflow_values_invalid` の
   `details.fields` を欄の下に出す。成功したら閉じ、送り先が別なら知らせる。
5. **管理は作らない** (作成・編集は Desktop / Web で)。止める / 再開もしない。
6. 試験: ベクタ (描き方・値の検査)、印のデコード (欄が無い・null・ある)、`/wf` の解釈、送信の再試行で同じキー。

### 8.1 M95 iOS (build 84)

- **ファイル**: 純粋な部分 `UI/Workflows.swift` (既定値・値の検査・描き方・`/` の解釈・`runBlockedText`)、画面
  `UI/WorkflowViews.swift` (印・一覧・フォーム)、モデルと API `Api/WorkflowModels.swift`、`App/AppController+Workflows.swift`
  (1 分の覚え・フォームを開く・送信の `WorkflowSubmitter`)。
- **印**: `MessageOut.workflow` / `MessageState.workflow` (欄が無い・null・知らない形でも読める。端末の保存にも残る)。
  名前の上に 1 行の「⚡ 名前」(行の高さは名前の長さで変わらない)。押すと `GET /workflows/{id}` を読み、実行できれば
  フォーム、できなければ理由 (`runBlockedText`) をエラーの帯に出す。消したメッセージには出さない。
- **一覧**: 入力欄の「＋」→「ワークフロー」(シート。選ぶとシートが閉じてからフォーム) と、チャンネル詳細の「ワークフロー」
  (ページ)。どちらも開くたびに読み、`AppController.workflowLists` に 1 分覚える。実行できないものは薄くして押せず、理由を添える。
  DM とスレッドの入力欄には出さない。
- **`/`**: 組み込み → テンプレート → ワークフローの順。`/` で始めると一覧を読み、候補の帯の最後に「⚡ /名前」(空白を含む名前は
  「/wf 名前」)。送信の `/名前`・`/wf 名前` は一覧を読んでから決める (読み終わる前に送っても開く)。
- **フォーム**: `MainView` の全画面 (`AppController.workflowRun`)。短文 `TextField`・長文 複数行・日付 / 時刻 / 日時は
  `DatePicker` (任意の欄は「日付を選ぶ」から始まり「クリア」で空に)・選択は `Picker`・人は `TaskAssigneePicker`
  (`multiple` でなければ 1 人)・チェックは `Toggle`。`client_msg_id` は最初の「投稿」で作り、フォームを閉じるまで使い回す。
  成功したら閉じ、開いた会話と送り先が違えば「#送り先 に投稿しました」。
- **試験**: `WorkflowsTests` 12 (ベクタ・印のデコード・`/wf`・同じキーの再試行・`details.fields`・1 分の覚え)、
  `WorkflowSnapshotTests` 2 (印・一覧・フォームの画像、印の高さ)。

## 10. 実装で決めたこと (M94)

- **管理者**: 送り先を読める管理者 (メンバー、または公開チャンネル) が管理できる。定期投稿 (RECURRING.md §7) はメンバーで
  ある管理者に限るが、あれはボットをチャンネルに入れるため。ワークフローは誰も入れないので、公開チャンネルなら参加していない
  管理者も管理できる。非公開チャンネルは参加していない管理者には見えない (`404 workflow_not_found`)。
- **冪等**: 送信は先に `client_msg_id` を見る。同じワークフローのメッセージがあれば、ワークフローが止められ・変えられ・
  消された後でもそれを 200 で返す (再送で失敗にしない)。別のワークフロー (またはふつうの投稿) に使ったキーなら
  `409 idempotency_conflict`。
- **値の検査の順**: 値の誤り (`workflow_values_invalid`) は投稿の権限 (`not_a_member` / `posting_restricted` /
  `channel_archived`) より先に出る (どちらも何も投稿しない)。
- **項目のない雛形**も作れる (決まった文を 1 回の操作で投稿する)。
- **Desktop のファイル名**: 純粋な部分は `ui/workflows.ts`、画面は `ui/WorkflowViews.tsx` (TypeScript は拡張子だけが違う
  同じ名前のファイルを片方しか読まず、macOS の大文字小文字を区別しないファイルシステムでは `Workflows.tsx` と
  `workflows.ts` が同じ名前になる)。
- **試験**: サーバ `tests/test_workflows.py` 28、Desktop `tests/workflows.test.ts` 37・`tests/workflowsUi.test.tsx` 10。
