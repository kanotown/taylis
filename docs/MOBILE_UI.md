## 1. 結論 (要約)

- **一番効くのは会話画面**。毎日何十回も触るのは会話画面なので、ここを先に直す。
  - 長押しの操作を下からのシートに統一する。上段にクイックリアクション、下にラベル付きの操作一覧。3 端末とも今は「長い縦メニュー / 小さなドロップダウン / ラベル無しのアイコン 13 個」とバラバラ。
  - 見出しのアイコンを減らす。Android は 7 個あり、題名が隠れる。
  - iOS のスレッドをシートからプッシュ遷移に変える。
  - サーバの変更は要らず、工数は M。
- **次にナビゲーションの骨格を作る**。下部タブを「ホーム / DM / アクティビティ / 自分」の 4 つにする。
  - ホームは上部に横スクロールのタイル (スレッド・下書き・保存・リマインダー・ファイル) を置き、その下は折りたためるセクション、右下に新規メッセージの作成ボタン。
  - 今の固定 6 行と「すべて/未読」の切り替えはやめる。
  - 工数は L。Android は MainScreen.kt の状態管理を作り直すことになる。
- **サーバの変更が要るのは 2 つ**。
  - DM 一覧のプレビュー: ChannelOut に `last_message` を足す。工数 M。
  - アクティビティのリアクション通知と既読の印: `GET /activity` と `activity_read_at` を足す。工数 L。
  - どちらもタブの骨格ができてから段階的に入れる。アクティビティは、最初は既存の `/mentions` と `/threads` だけで出す。
- iPad / タブレット / Desktop の広い画面は、今のサイドバー型のままにする。タブ型にするのはスマホ幅だけ。Android タブレットのレール + ペインは §12 (M110)、iPad のサイドバー + 会話 + スレッドのペインは §13 (M109)。

## 5. 新しい情報設計 (スマホ幅)

```
TabView / NavigationBar (4 タブ、会話・スレッドの中ではタブバーを隠す)
 ├ ホーム      NavigationStack: Home → 会話 → スレッド / チャンネル詳細 / プロフィール
 ├ DM          NavigationStack: DM 一覧 → 会話 → スレッド
 ├ アクティビティ NavigationStack: Activity → 会話 (該当位置) / スレッド
 └ 自分        NavigationStack: You → 通知 / 表示 / プロフィール編集 / アカウント / ワークスペース
全画面で重ねるもの: 移動・検索 (ホーム上部から)、新規メッセージ (FAB)、画像ビューア
```
- 2026-10-27：Android は 5 タブ（ホーム・DM・アクティビティ・**検索**・自分）。ホームの「移動・検索」は「検索」タブに切り替える（§28.1）。
- 2026-10-27：iOS も同じ 5 タブ。ホームの「移動・検索」は「検索」タブに切り替える（§28.2）。iPad の分割ではタブの代わりにサイドバーの「検索」の行。
- 開いているタブをもう一度押すと、そのタブの先頭に戻る。先頭にいるときは一番上までスクロールする (Slack と同じ)。
- 通知をタップしたときの行き先:
  - DM: DM タブのスタックを [会話] に置き換える
  - チャンネル / スレッド: ホームタブのスタックを [会話, (スレッド)] に置き換える
  - アクティビティの行から開いたもの: アクティビティのスタックに積む
  - スレッドの返信（メンション・保存済み・Times フィードの行、通知、パーマリンク）は、会話とスレッドを一度にスタックに積み、スレッドの画面だけがすぐ出る。途中で会話の画面を見せない。戻ると会話、もう一度戻ると一覧（2026-10-06。iOS は前は会話を開いてから会話がスレッドを開く 2 段の動きだったのを `MainNavigation.show` / `land`、`MainRoute.thread` で直した。iPad の分割ではこれまでどおり会話の横のペインに開く。Android は `MainNav.openConversation` / `MainTabs.land` が［会話, スレッド］を一度に置くので、もともとこの形）
  - アクティビティの行から開いたスレッドの返信は、戻るでアクティビティに 1 回で戻る（2026-10-09。「スレッド」一覧から開いたときと同じ）。それまでは戻ると会話、もう一度戻るとアクティビティだった。iOS は `MainNavigation.showFromActivity` がスレッドの画面だけを積む。Android は `revealFromActivity` が［会話, スレッド］を `ThreadFrom.LIST` で置き、戻るで両方を外す。どちらもスマホの幅だけで、iPad・タブレットの分割ではこれまでどおり会話の横のペインに開く。Desktop / Web の狭い幅はもともとアクティビティの上にスレッドを出して戻るでアクティビティに戻る。通知から開いたスレッドは上のとおり会話の上に積む（戻ると会話）
  - 開いている画面の中のメッセージへのリンク（スレッドの中から同じスレッドの返信・親へ、会話のタイムラインから同じ会話のトップレベルのメッセージへ）は移動せず、その場でそのメッセージまでスクロールして強調する。足りない返信は読み直す。同じリンクをもう一度押しても（スクロールしたあとでも）そこへ戻る。それ以外のリンク（別のスレッド、別の会話、キャンバスなどの中のリンク）はこれまでどおり上の着地（2026-10-21 のユーザー報告。前はスタックを同じ形に置き直すだけで、開いているスレッドは一度置いた位置から動かず、親へのリンクはスレッドを閉じて会話に移っていた。iOS は `PermalinkJump` / `MessageLinkContext`（環境値）と `ThreadView.jumpToFocus`、Android は同名の `PermalinkJump` / `LocalMessageLinkContext` と `ThreadPane` の `focusRequest`。Desktop / Web はもともとスレッドのペインがフォーカスの変化でその行へスクロールする）
- 広い画面は今のサイドバー型 (iOS の NavigationSplitView、Android と Web の 2〜3 列) を続ける。サイドバーに「アクティビティ」(今の「メンション」を置き換え) と「DM」を足して、中身を揃える。

### 5.1 横のスワイプで会話と一覧を行き来する (GitHub issue #1、2026-10-06)

Slack と同じく、スマホ幅 (Android の `PaneLayout.PHONE`、iOS の `MainLayout.tabs`) では横のスワイプで会話と一覧を行き来する。タブレット・iPad の横に並ぶ形は一覧が見えているので変えない。

- **戻る (右へ)**：会話 (「メッセージ」タブで詳細を開いていないとき) とスレッドの画面のどこからでも。行き先は ← と同じ (一覧・検索結果・スレッドの元の会話、`MainTabs.back`)。会話のほかのタブ (キャンバス・タスクのボードなど) と詳細は横の中身があるので取らない。
- **進む (左へ)**：タブの先頭 (ホーム・DM・アクティビティ、自分は除く) で、そのタブで最後に閉じた会話を開く。覚えるのはタブのスタックから会話が無くなったとき (←・戻る・スワイプ・タブの再タップ。別の会話に置き換えたときは覚えない)。ストアに無い会話・シートやダイアログ・移動・検索の間は進まない。
- **動き**：画面が指についてくる。下の画面は左へ 30% ずれたところから戻り (パララックス)、最大 18% 暗くする。幅の 40% を超えるか、速いフリック (700 dp/s・pt/s) で完了、そうでなければ戻る。
- **取り合い**：はっきり横 (30° 以内、タッチスロップを超えてから) のときだけ取る。縦のスクロール・文字の選択・入力欄・横にスクロールできる中身 (コードブロック・表・リアクションの行・ホームのタイル) が先に取ったら取らない。Android では左端まで来た横スクロールの残りをネストスクロールで受けて戻るスワイプにする。
- **設定**：自分 →「表示」→「操作」→「スワイプで戻る・進む」(端末ごと、既定オン)。オフでも端の戻るジェスチャーは残る。
- **Android** (`ui/SwipeNav.kt` の規則、`ui/SwipeNavHost.kt`)：スワイプの間だけ行き先のページ (バー・中身・タブバーの一式) も描き、ページを `SwipeNav.pageKey` で鍵にして、下にあったページが上になっても状態 (スクロール位置・タイムライン) を保つ。端の戻るジェスチャーも同じスライド (予測型の戻る `PredictiveBackHandler`、`enableOnBackInvokedCallback`)、3 ボタンの戻るは同じスライドを一気に。
- **iOS** (`UI/SwipeNav.swift`)：戻るは iOS 26 の UIKit の `interactiveContentPopGestureRecognizer` (画面のどこからでも、横スクロールの上では失敗し、キーボードは画面と一緒に去る。KeyboardBehavior.swift が既に見ている)。iOS 17・18 は端からだけ (私有 API の全画面化はしない)。設定はこの認識器の有効・無効も切り替える。進むは各タブの NavigationStack に付けた `UIPanGestureRecognizer` (先頭のときだけ、縦のスクロールはこれの失敗を待つ) で、会話の見出しの形のページが右から指についてきて、離すとアニメーションなしで会話を積み、そのページを消す。
- **試験**：方向・角度・閾値・行き先・覚える会話の単体試験 (Android `SwipeNavTest`、iOS `SwipeNavTests`)。Android はエミュレータで `adb shell input` のドラッグ (両方向・途中で戻す・縦スクロール・端の戻る・設定オフ)、iOS はシミュレータの使い捨ての XCUITest で確かめた。

## 6. 画面ごとの仕様

### 6.1 ホーム
```

├──────────────────────────────────┤
│ ▾ 未読              (「未読をまとめる」ON のとき)│
│ ▾ お気に入り                             │
│ ▾ 〈自分のセクション〉            ⋯        │
│ ▾ チャンネル                              │

│   🔒 m2-進捗                   (2)      │ ← 44pt/48dp の 1 行。未読は太字、メンション数は赤い丸、ミュートは 55%
```

### 6.4 アクティビティ
```
│ アクティビティ 未読 3 件   [✓✓ すべて既読にする] │ ← 2026-10-07: 見出しに数とボタン（⋯ のメニューはやめた）
│ [すべて][メンション][スレッド][リアクション]       │
│                                  (● 未読のみ) │
│ ● (av) 山田先生 · #輪講 · 10:05             │
│        @あなた 来週の発表順を…                │
│ ● 💬 「学会の締切」 3 件の新しい返信 · #m2-進捗   │
│   (av) 佐藤 ほか 2 人が 👍 「スライド v2 です」    │
```
- **段階 A (サーバ変更なし)**:
  - フィルタは [メンション | スレッド] の 2 つ
  - メンションは `GET /mentions` を使い、行は既存の MessageCardView
  - スレッドは `GET /threads` を使い、行は既存の ThreadRowView / ThreadsPane
  - タップしたら revealMessage / スレッド画面を開く
  - タブのバッジは今の threadSummary と、メンションのある会話の数で出す
- **段階 B (7.2)**: 「すべて」と「リアクション」を足し、項目ごとに未読の点、「すべて既読」を付ける。
  - 未読は `activity_read_at` より新しい項目。端末をまたいで同期する
  - タブのバッジは未読の項目数。メンションを含むときは赤
  - **会話で読んだものは既読（2026-10-06、Slack と同じ）**。メンションやスレッドの返信を会話・スレッドで読んだのに、アクティビティのバッジに数えられたままだった。項目が未読なのは次の両方を満たすとき：
    1. `at` が `activity_read_at` より新しい（今までどおり。「すべて既読」はこれで全部を既読にする）
    2. 項目の種類が `mention` か `thread_reply` なら、そのメッセージが自分にとって会話でまだ読まれていない：
       - タイムラインの行（`parent_id` が null か、`also_in_channel` が true の返信）は、会話の既読位置（`read_states.last_read_seq`、`read.updated` / bootstrap の `last_read_seq`）が `seq` より小さい
       - スレッドの返信（`parent_id` がある）は、そのスレッドの自分の既読位置（`thread_follows.last_read_seq`、`ThreadState.last_read_seq`。フォローしていなくても読めば行ができる。行が無ければ 0）が `seq` より小さい
       - 「チャンネルにも送信」した返信はどちらか一方で読めば既読（上の 2 つの両方がまだのときだけ未読）
       - 既読位置は自分のものだけを見る（他の人が読んでも変わらない）。「ここから未読にする」（`mode: "set"`）で位置が戻れば、`activity_read_at` より新しい項目はまた未読になる
    - `reaction`・`canvas_mention` は 1 だけ（メッセージの既読位置とは関係しない）。`reservation` は 1 かつ「対応済み」でない（M112 のまま）
    - サーバは `GET /activity/summary`・bootstrap の `activity`・`PUT /activity/read` の応答の `unread_count` / `mention_unread` をこの規則で数え、`GET /activity` の各項目に `read: bool` を付ける（同じ規則。null・無しはこの規則より前のサーバなので `at` と `read_at` を比べる）。2026-10-07 からは下の「開いたら既読」も加わる
    - クライアント：未読の点は `read` で出す。接続中に `read.updated`（自分の会話の既読位置）と `thread.updated`（`reason: "read"`、自分のスレッドの既読位置）、`threads.read_all`（2026-10-09、スレッドのすべて既読）を受けたら、今のメンション・返信の `message.created` と同じくまとめて（デバウンスして）`GET /activity/summary` を取り直す。一覧を表示・保持していれば、上の 2 の規則でその場で項目の `read` を true にしてよい（`channel_id` と `last_read_seq`、または `parent_id` と `last_read_seq` で該当する項目）。`reason: "set"` で位置が戻ったときは一覧を読み直す
    - アプリのアイコンのバッジ（プッシュの `badge`）はアクティビティの数を含まない（PUSH_NOTIFICATIONS.md §4.2）ので、この規則で変わらない
  - **開いたら既読（2026-10-07、Slack と同じ）**。利用者の声：「アクティビティの通知がいつ消える（既読になる）のかわかりにくい」。それまでは
    タブを開いて約 1.5 秒で `activity_read_at` が進み（「すべて」のとき）、見ただけで全部が既読になっていた。これをやめる。
    **項目は次のどれかまで未読**（太字・点・「未読 n 件」とバッジに数える）：
    1. **その項目を開いた**（一覧の行をクリック・タップ）。`PUT /activity/items/read` `{item_ids}`
       - 2026-10-12：開いた項目が自分宛てのメンションなら、サーバはその会話（返信ならスレッドも）の既読位置もそのメッセージまで
         進める。チャンネル・スレッドのメンションのバッジが全端末で消え、後の未読は残る（SYNC_PROTOCOL.md §10.7）
    2. メンション・スレッドの返信は、そのメッセージを会話・スレッドで読んだ（上の 2026-10-06 の規則のまま）
    3. **「すべて既読にする」**を押した（見出しのボタン。`PUT /activity/read`、`read_at` は今。既読位置より前は全部既読）
       - これはアクティビティの項目だけを既読にし、スレッドの既読位置（「スレッド」の未読）は動かさない。スレッドは「スレッド」一覧の見出しの「すべて既読にする」（`POST /threads/read-all`、THREADS.md §3.2、2026-10-09）で読む。そちらで読んだスレッドの返信・メンションの項目は上の 2 で既読になる（他端末へは `threads.read_all`。受けたらアクティビティのバッジを取り直す）
    4. 予約の担当者の作業は「対応済み」になった（RESERVATIONS.md §5 のまま）

    **一覧を表示する・スクロールするだけでは何も既読にしない**（`PUT /activity/read` を自動で送らない）。
    - **項目の id**：`GET /activity` の各項目の `id`（uuid）。`mention`・`thread_reply`・`reaction` はそのメッセージの id、
      `canvas_mention`・`page_mention`・`page_shared`・`reservation` はその項目の `item_id`（`canvas.item_id` など）。
      `id` の無い項目はこれより前のサーバのもの（開いても送らない。既読位置で既読になるのを待つ）
    - **開いた項目の既読**：サーバは `activity_item_reads(user_id, item_id, read_at)` に開いた時刻を残す（DATA_MODEL.md）。
      項目は `at` ≦ その時刻のあいだ既読。**リアクションの項目は、あとで誰かがリアクションすると `at` が進むので未読に戻る**
      （Slack と同じ。キャンバス・ドキュメントのメンションは開いた後のメンションが新しい項目になる）
    - `PUT /activity/items/read`：`{item_ids: [uuid]}`（1〜100 件）、`include` は他と同じ。冪等。自分の項目でない id は黙って捨てる。
      応答は `ActivitySummaryOut`（新しいバッジ）。自分の全端末に `activity.items_read` `{item_ids, read_at}`（user 宛て、seq なし）
    - `PUT /activity/read`（すべて既読にする）はそのまま。既読位置を進めたとき、その位置以前の `activity_item_reads` を消す（表が育たない）
    - `GET /activity` の `read`・summary の数・bootstrap の `activity` は 1〜4 の全部で求める
    - **クライアントの規則**（Web・Android・iOS は実装済み（2026-10-07）。Android は見出しの下のフィルタの列の最後に「未読のみ」、⋮ の「すべて既読」はやめた）：
      - 行の点と太字：`read == false` かつ `at` > 今持っている `read_at`（store の `activity.read_at`。他端末の「すべて既読にする」で
        `activity.read` が来たら進む）かつ「開いた項目」（下）で既読でない かつ（メンション・返信は）会話で読んでいない。
        `read == null` のサーバは `at` と `read_at` だけ
      - 行を開いたら：その場で「開いた項目」に `id → at`（その行の `at`。端末の時計は使わない）を入れて点を消し、
        `PUT /activity/items/read` を送り、応答をバッジにする。それから行の中身（会話・スレッド・キャンバス・ページ・予約）を開く。
        メンション・返信は会話を開けば読めるが、すぐ消えるようにこれも送る
      - `activity.items_read` を受けたら「開いた項目」に `id → read_at`（進むときだけ）を入れ、まとめて `GET /activity/summary` を取り直す
      - 見出し：「未読 n 件」（`unread_count`、99 は「99+」。0 なら「未読はありません」）と「すべて既読にする」（0 のときは押せない）。
        「すべて既読にする」は `read_at` = max(今, 持っている行の一番新しい `at`)
      - 既読の行はふつうの字（名前は medium、本文は薄い色）、未読の行は太字・左の点・薄い色の背景
      - 「未読のみ」：持っている行から既読の行を除く（端末の中だけ。開いた行は一覧から消える）。空なら「未読のアクティビティはありません」
    - **互換**：これより前のクライアント（Android・iOS の 2026-10-07 より前の版）は今までどおり表示すると `PUT /activity/read` を送るので、その端末で
      開けば全部既読になる（`activity.read` で他の端末も既読になる）。これは受け入れる（それらの版が新しい規則に合わせるまで）
    - **これより前のサーバ**（項目に `id` が無い）：新しいクライアントは表示しても自動で既読にしない（Web・iOS とも、自動の既読はサーバを
      問わずやめた）。行を開いても何も送らず、点は「すべて既読にする」か（メンション・返信は）会話で読むまで残る。サーバによって
      自動の既読を残すと、同じアプリで既読の規則が二通りになり分かりにくいので、これを選んだ（iOS、2026-10-07）
    - iOS（2026-10-07）：見出しの「すべて既読にする」はナビゲーションバーの右、「未読 n 件」と「未読のみ」は表示の切り替えの下の 1 行。
      iPad のサイドバーの「アクティビティ」の数もタブのバッジも同じ `unread_count` に従う
- 研究室向けの候補: 「確認依頼」フィルタ。確認を求められていて自分がまだ確認していない投稿 (M15e の ack) を出す (決定事項 3)。

## 7. データモデル / API の変更 (P2 以降、OpenAPI と docs も一緒に更新する)

### 7.1 DM (と会話) のプレビュー
- `ChannelOut.last_message: {id, sender_id, type, seq, excerpt, has_attachments, created_at} | null` を足す (M49 で実装)。
  - 対象はトップレベルと `also_in_channel` の投稿で、削除済みは除く
  - excerpt はサーバの `notification_text()` (messages/mentions.py) で作る。メンションを名前にして 140 文字まで。本文が無ければ `attachment_text()`。プッシュの本文と同じ規則になる
  - `seq` は取り直しの応答と手元の値の新旧を比べるため、`type` は system メッセージに先頭を付けないため
- 返すのは **会員に向けた応答だけ** (bootstrap と `GET /channels`・`GET /channels/{id}`・既存の DM を返す `POST /dms`)。
  - `channel.updated` は非会員にも配ることがある (M15b) ので、ここには含めない。他の応答とイベントでは常に null で、クライアントは持っている値を残す
  - DM に限らず会員の会話すべてに入れる。1 会話 1 回のインデックス参照で、DM だけに絞っても問い合わせの数も時間もほぼ変わらないため。クライアントが出すのは今は DM 一覧だけ
- クライアントでの更新 (SYNC_PROTOCOL.md §7.8):
  - `message.created` (タイムラインの行) が来たら置き換える。**`synced_seq` が null の会話でも更新する**
  - `message.updated` で同じ id なら本文を差し替える
  - `message.deleted` で同じ id なら、持っているタイムラインのその前の行にする。持っていなければ `GET /channels/{id}` を取り直す
- 性能: LATERAL で (channel_id, seq) の一意インデックスを逆順にたどる (マイグレーション不要)。chikuwa_perf (103 会話・47 万件) で全会話 1 クエリ 1 ms (温まった状態、初回 24 ms)。bootstrap の問い合わせの数は会話の数で増えない (テストあり)。重くなったら `channels.last_message_id` を last_message_at と同じトランザクションで更新する (messages/repository.py の allocate_seq)。

### 7.2 アクティビティ (段階 B)
- `GET /api/v1/activity?filter=all|mentions|threads|reactions&cursor=&limit=50`
  - 返す形: `{items:[{kind:"mention"|"reaction"|"thread_reply", at, message: MessageOut, actor_ids:[…], emoji?, thread?}], next_cursor, read_at}`
  - mention は既存の `/mentions` の問い合わせ、reaction は `reactions ⋈ messages (sender_id = 自分, reactions.user_id ≠ 自分)`、thread_reply はフォロー中のスレッドの新しい返信。これらを `UNION ALL` して、(at, kind, id) のカーソルで並べる
  - 今参加している会話だけに絞る。削除済みは除く。ゲストの見える範囲も守る
  - 必要なら `reactions (created_at)` にインデックスを足す
- `PUT /api/v1/activity/read {read_at}` を足す。read_state と同じく大きい方にだけ進める (max-merge)。
  - 自分の他の端末には `activity.read` (audience=user) を送る
  - bootstrap に `activity: {read_at, unread_count}` を足す。他のワークスペースのバッジ用に `GET /sync/summary` にも足す
- M76: `kind: "canvas_mention"` (キャンバスでのメンション、`message` は null で `canvas` がある) は `include=canvas_mention`
  を付けた端末にだけ返し、数える (CANVAS.md §20)。
- 保存するのは `users.activity_read_at timestamptz` の 1 列だけ (マイグレーション 1 本)。
  - 項目ごとに既読の行は作らない (CLAUDE.md の ReadState と同じ考え方)
  - 2026-10-06：メンションとスレッドの返信は、会話・スレッドの既読位置で読んだものも既読（§6.4）。数える問い合わせは既読位置を主キーで 1 回ずつ引くだけで、メンションは GIN と `messages_mention_all_idx` で引く（`mention_all` の条件を部分インデックスの述語 `mention_all AND deleted_at IS NULL` の形で書く）。40 万件・既読位置 200 日前の合成データでメンション 2〜5 ms、返信はフォロー中のスレッド数に比例（1.2 万スレッドで約 25 ms、数百なら 1〜5 ms）。マイグレーション不要
  - 2026-10-07：開いた項目だけは `activity_item_reads` に行を作る（§6.4「開いたら既読」、マイグレーション 0099）。CLAUDE.md の
    「読んだメッセージごとに行を作らない」に反しないよう、行は利用者が一覧で開いた通知の分だけ・既読位置より後の項目だけで、
    「すべて既読にする」で位置を進めるとその位置以前の行を消す（メッセージの既読は今までどおり read_states の位置）
- 接続中の件数:
  - クライアントがイベントから数える。メンションの `message.created`、自分の投稿への `message.updated change=reaction`、`thread.updated`
  - 再接続したら bootstrap の値で直す (WS だけに頼らない)

   - 対策: 「選ばれているタブの一番上の画面であること」を条件に加える。`engine.currentChannelId` (MainView.swift:119-124) もその画面だけが設定する
   - Android も同じ (ChannelPane.kt:109-121)
2. **通知タップとリンクの行き先**。
   - `chikuwaOpenChannel` (MainView.swift:125-138)、`pendingChannelId` と `pendingReveal` (MainScreen.kt:168-175,275-279) を、タブを選ぶ処理に書き直す
3. **Android の作り直しで既存の挙動が壊れる**。
   - M16b の「検索結果に戻る」(backToSearch / searchThread、MainScreen.kt:104-107,234-262)、ワークスペースごとの状態保存 (AppRoot.kt:33) を保つ
   - 状態遷移を純粋関数にしてテストする
4. **iOS 17 の制約**。選択範囲の binding と Tab API は iOS 18 から。書式バーは UIKit のラッパーで作るか、最低バージョンを上げる。
5. **プライバシー**。
   - `last_message` を非会員に向けたイベントに入れない
   - アクティビティは退出した非公開チャンネルの項目を返さない
   - ゲストの見える範囲を守る
6. **性能**。
   - ホームのセクションは描画のたびに再計算しているが、数十会話なら問題ない
   - タブごとに会話画面を生かしておくとメモリが増える。タブを切り替えたら会話の timeline 計算を止めるか、前面のタブ以外はスタックを浅くする
   - アクティビティの UNION は計測してからインデックスを決める
7. **アクセシビリティの後退**。contextMenu をやめても、VoiceOver と TalkBack のカスタムアクションで同じ操作ができるようにする。タップ領域は 44pt/48dp 以上。
8. **3 端末の差**。仕様表 (8 章) を IMPLEMENTATION_PLAN に載せ、契約テストの fixture と各端末のスナップショット/目視で確かめる。
9. **研究室向け機能との重なり**。times やキャンバスの入口 (ホームのタイル、会話のタブ列) をこの設計で空けておき、別途の設計と合わせる。

## 12. Android タブレット (M110、2026-10-05)

§1 の「広い画面はサイドバー型のまま」を Android でも形にした。スマホ幅の画面 (下部タブ・1 画面ずつ) はそのまま。

### 12.1 どの形になるか (`ui/AdaptiveLayout.kt`)

| 窓 (dp) | 形 |
|---|---|
| 幅 < 600、または高さ < 480 (スマホを横にしたとき) | スマホの画面 (変更なし) |
| 600 ≤ 幅 < 840 の縦長 (7" / 10" タブレットの縦) | スマホの画面 |
| 600 ≤ 幅 < 840 の横長、840 ≤ 幅 < 1140 (7" の横、開いたフォルダブル) | 2 ペイン: レール + 一覧 + 本文。スレッドは本文のペインを覆う (← で会話へ) |
| 幅 ≥ 1140 (10" の横) | 3 ペイン: レール + 一覧 + 会話 + スレッド (380dp、✕ で閉じる) |

- レール (NavigationRail): 下部タブと同じ 4 つ (ホーム / DM / アクティビティ / 自分) と同じバッジ、先頭に ✏️ 新しいメッセージ。2026-10-27 から「検索」を足した 5 つ。「検索」タブは一覧のペインを使わない (§28.1)。
- 一覧のペイン (300dp、幅 1000dp 以上で 340dp): 選んだタブの根 (ホームのタイルとセクション・ワークスペースの切り替え・⋮、DM 一覧、アクティビティ)。開いている会話の行に色が付く。
- 本文のペイン: 一覧から開いたもの (会話とそのタブ・詳細、タイルの一覧、検索・移動)。何も開いていなければ「左の一覧から…を選んでください」。← は根の上にさらに何かあるとき (「スレッド」一覧や検索結果から開いた会話) だけ出す。
- 自分のタブは一覧のペインを使わず、M40 の 2 ペイン (一覧 + 設定画面) を全幅に出す。
- ログイン画面のフォームは幅 560dp まで。

### 12.2 状態は 1 つ (形が変わっても失わない)

- 戻るスタック (`TabStacks` / `MainNav`) は形によらず同じ。形は「スタックのどのルートをどのペインに描くか」だけを決める: 根は一覧、最上段のスレッドは (3 ペインなら) スレッドのペイン、残りは本文。回転・フリーフォームの窓の大きさの変更・フォルダブルの開閉で、開いている会話とスレッドがそのまま残る (写し替えは無い)。通知・パーマリンク・検索結果は `MainTabs.land*` のままで、広い画面ではペインに開く。
- 広い画面だけの遷移: タイル (と Times の「フィード」) は本文を置き換える (`openFromList`、スマホは積む)。スレッドを開いたまま別のスレッドを開くと置き換える (`openThread`)。スレッドのペインの ✕ はスレッドだけ閉じる (`closeThread`、「スレッド」一覧から開いたものでも会話は残る)。会話の詳細・タブ・キャンバスの切り替えは横のスレッドを先に閉じる (`surfaceConversation`)。
- タイムラインの既読 (SYNC_PROTOCOL.md §10.1 2.): 3 ペインではスレッドを開いていても会話のタイムラインは見えているので「画面にある」(`AdaptiveLayout.conversationOnScreen`)。
- 一覧と本文 (とスレッド) は同時に描くので、形が変わると本文のスクロール位置は作り直しになる (開いている会話・スレッド・下書きは残る)。

### 12.3 ハードウェアキーボード (`ui/HardwareKeys.kt`)

- 入力欄: ハードウェアキーボードがつながっているとき (Configuration の `keyboard = QWERTY` かつ `hardKeyboardHidden = NO`) だけ Enter で送信、Shift+Enter で改行。IME が変換中 (かなの未確定) の Enter は IME のもの。スマホの画面のキーボードでは今までどおり Enter は改行。
- Ctrl+K (Meta+K): どの画面からでもホームのタブの「移動・検索」(`MainActivity.onKeyShortcut` → `AppController.pendingJump`)。Meta+/ のショートカット一覧にも出す。
- 注意: エミュレータで `adb shell input keyevent 66` を送ると、Gboard の画面のキーボードが出ている間は Gboard が Enter を受けて改行にする (IME を止めると送信になるのを確かめた)。実機のキーボードカバー / Bluetooth キーボードでの確認はまだ。

### 12.4 マニフェスト・ダイアログ

- `resizeableActivity="true"` を明示 (画面の向きの固定は元から無い)。レターボックスにならない。
- 下からのシート (長押しの操作など) は Material 3 の `ModalBottomSheet` の既定 (幅 640dp まで、中央) のまま。ダイアログはもともと中央に出る。

### 12.5 試験

- `AdaptiveLayoutTest` (形の判定、ペインへの割り当て、回転でスタックが変わらないこと、通知の着地、広い画面の遷移、既読、Enter / Ctrl+K の判定)。
- エミュレータ: Pixel Tablet (2560×1600、API 36) の横 (3 ペイン) と縦 (スマホの画面)、`wm size 1920x1200` + `wm density 320` (7"、2 ペイン)、ChikuwaChat_Pixel_9 (変わらないこと、横でもスマホの画面)。

## 13. iPad (M109、2026-10-05)

iOS のアプリを iPhone と iPad の両方で動かす (`TARGETED_DEVICE_FAMILY = "1,2"`)。iPad では向きの 4 つすべてと Split View・Slide Over・Stage Manager に対応する (`UISupportedInterfaceOrientations~ipad` に 4 つ、`UIRequiresFullScreen` は無し)。サーバの変更はない。

### 13.1 どの形になるか (`UI/MainNavigation.swift` の `MainLayout`)

- 横のサイズクラスで決める。compact (iPhone、iPad の狭い Split View / Slide Over / 小さな Stage Manager の窓) は今までのスマホの画面 (下のタブ 4 つとプッシュ)。regular は Slack のような分割 (`NavigationSplitView`)。
- regular でも窓が 700 pt より狭ければスマホの画面（2026-10-24、§26.2：iPhone Duo の内側の縦長 669 pt、regular のまま 700 pt に満たない
  Stage Manager の窓）。サイドバーの 320 pt を引くと会話が狭すぎ、Duo では分割のレイアウトが固まった。
- 分割の左 (サイドバー、320pt): ホームの一覧そのもの (ワークスペース名・自分のアバター・⋯・移動・検索・タイル・セクション・✏️) に、タブの代わりの「アクティビティ」の行 (バッジ付き) を足す。2026-10-27 からその下に「検索」の行（メッセージの検索のシートを開く。§28.2）。開いている会話・一覧の行とタイルに色を付ける。
- 右 (本文): サイドバーで選んだもの (会話・スレッド一覧・保存・下書き・ファイル・Times フィード・カレンダー・タスク・アクティビティ・すべての DM)。一覧から開いた会話は本文の上にプッシュ (戻るで一覧)。選んでいないときは「会話を選んでください」と ⌘K / ⌘N の案内。
- スレッドは本文の右のペイン (`inspector`、幅 340〜520pt、既定 400pt)。プッシュしない。会話のタイムラインは見えたままなので既読の判定 (SYNC_PROTOCOL.md §10.1 2.) でも「画面にある」。ペインの上の 1 行に「スレッド / #会話」と ✕。フォローと ⋯ は inspector と本文が共有するナビゲーションバーの右端 (ペインの上) に出る。
- 幅が 1180pt 未満 (iPad の縦、狭い窓) でスレッドを開くと、サイドバーを一時的にしまって会話とスレッドの 2 列にし、スレッドを閉じると戻す (`MainNavigation.sidebarStepsAside`)。13" / 11" の横は 3 列のまま。
- サイドバーの表示・非表示（2026-10-14）：サイドバーのバーの右端に「サイドバーを非表示」（`sidebar.left`）、しまっている間は本文のどの画面（会話・スレッド・一覧・ドキュメント・「会話を選んでください」）のバーの左端にも「サイドバーを表示」を出す。システムのトグルは外して自前のボタンにする（13.4）。⌃⌘S でも切り替える（`SidebarCommands`）。
- 手で変えた方が勝つ（`SidebarVisibility`）：スレッドのためにしまったサイドバーを手で出したら、そのスレッドを開いている間は回転してもしまわない。スレッドの前から手でしまっていた、またはスレッドを開いている間に手でしまい直したサイドバーは、スレッドを閉じても出さない。次にスレッドを開くと、また自動でしまう。
- 自分 (設定) は分割ではシート (`YouView` の「閉じる」付き)。左上の自分のアバターはステータスのメニュー（PRESENCE.md §11、2026-10-09）を開き、自分へはそのメニューの「設定」から行く。
- 新規作成・検索・ワークスペースの切り替えなどのシートは iPad では画面中央のフォームシート (システムの既定)。入力欄の絵文字ピッカーは regular では入力欄から出るポップオーバー、compact ではシート (`adaptivePopover`: 両方を付けておき、形が変わってもビューの状態を失わない)。長押しの操作・リアクションのシートは行に付いていないのでフォームシートのまま。

### 13.2 状態は 1 つ (形が変わっても失わない)

- `MainNavigation` (値型) がタブ・タブごとのスタック・分割の本文のスタック・自分のシート・開いているスレッドを持つ。形が変わると `setLayout` が写す: タブのスタック ⇄ 本文のスタック (DM タブは「すべての DM」、アクティビティは「アクティビティ」を先頭に)、DM の会話は DM タブへ、自分のタブ ⇄ 自分のシート。開いていたスレッドは新しい形の会話でもう一度開く (`pendingThread`)。
- 通知・パーマリンク・検索結果・新しい DM の着地 (`land`) は分割では本文をその会話だけにする (自分のシートは閉じる)。カレンダー・タスクの通知も本文に一覧を開く。
- 形の変更はアプリが前面にいるときだけ写す (`scenePhase != .background`)。App スイッチャーのスナップショットのためにバックグラウンドでサイズクラスが行き来しても、開いている会話を作り直さない (RootView の外観と同じ理由)。
- 会話・スレッドのビューは形が変わると作り直す (下書きは Store にあるので残る)。2026-10-24 から、一覧の位置・入力中のキーボード・
  会話のタブ（ドライブのタブのフォルダも）・チャンネルの詳細・メッセージのシートも新しい形のビューに引き継ぐ（§26.2 の `LayoutCarry`）。
  それまではスクロール位置が最初の位置に戻っていた。

### 13.3 ハードウェアキーボード・ポインタ

- アプリのメニュー (`.commands`、⌘ を長押しで一覧): ⌘K 移動・検索、⌘N 新しいメッセージ、⇧⌘F メッセージを検索、⌘[ 戻る (本文・タブのスタック)、⌘W スレッドを閉じる (分割)。シートが出ている間は無視する。
- ⌃⌘S サイドバーの表示・非表示（システムの `SidebarCommands`、2026-10-14）。これを足すまでは iPad に ⌃⌘S は無かった。
- 入力欄: ⌘Return で送信 (入力中の入力欄だけ。会話とスレッドの入力欄が並んでも重ならない)。Return は改行のまま。Desktop の既定 (`mod-enter`) と同じで、日本語の変換の確定の Return を送信と取り違えない。Enter で送信する設定は作っていない (変換中の Return を SwiftUI から見分けられないため。Android は M110 で IME の変換中を見分けて Enter 送信)。
- ポインタ: サイドバーの行・タイル・アクティビティの行・送信ボタン・✏️ にホバーの効果。

### 13.4 直した不具合

- 会話とスレッドのリストの幅を `containerRelativeFrame(.horizontal)` から外側の `GeometryReader` の幅 (`frame(width: viewport.size.width)`) に変えた。分割の本文の中では `containerRelativeFrame` がレイアウトを終わりなく繰り返し、会話を開いたとたんにアプリが固まった。スレッドの inspector も会話のビューの中に付けると同じように固まったので、MainView の本文の `NavigationStack` に付ける。
- iPad でサイドバーをしまうと出せなくなった（2026-10-14、利用者の報告）。iOS 26 では本文の列に `inspector`（スレッドのペイン）が付いていると、ペインを閉じていても、システムが本文のバーに「サイドバーを表示」のトグルを出さない（iOS 27 では出る。inspector を外すと iOS 26 でも出る）。iOS 26 の iPad ではサイドバーのトグル・スレッドの自動の非表示でしまうと、戻す手段が無かった（⌃⌘S も無く、端からのスワイプもシミュレータでは出せなかった）。システムのトグルを `.toolbar(removing: .sidebarToggle)` で外し、サイドバーに「サイドバーを非表示」、本文の各画面に「サイドバーを表示」を自前で付けた（OS によってトグルが 2 つ並ばないように、どの版でも自前にする）。あわせて自動の非表示が手の変更を打ち消さないようにした（13.1）。

  （iOS 26.5）で測ると、本文の列の `NavigationStack` は外から渡したパスのうち、積む・1 つ戻るには従うが、2 つ以上を一度に外す変更と、
  最初の画面が替わったときにその上に積んだ画面を外す変更には従わない（`@State` のパスや、アニメーション無しでも同じ。電話のタブは
  すべて従う）。そうした変更では本文の列のスタックを作り直す（`MainNavigation.splitStackRebuilds`、スタック自身が書いた変更＝戻る・
  戻るの長押しのメニューは除く）。

## 14. サイドバーの項目・ホームのタイルを選ぶ (M111、2026-10-05)

利用者の要望: サイドバーの項目が多く、人によって使わないものがある。各自が表示・非表示と順番を選び、すべての端末で同じにする。

### 14.1 保存と同期

- 1 人に 1 つのリスト `UserMe.nav_items` (`users.nav_items` jsonb、移行 0083): `[{key, visible}]` を順に。`null` = 既定。`PATCH /users/me {nav_items: [...] | null}` で丸ごと置き換える (64 個まで・key は `^[a-z][a-z0-9-]{0,31}$`・重複は 422 `validation_error`)。サーバは key を検査しない (知らない key = 新しいクライアントの項目もそのまま保存)。
- bootstrap の `me` に載る。変更は他の設定と同じく `user.updated` (UserPublic、リストは載らない) を出し、自分についての `updated_at` が新しければ別の端末が `GET /users/me` を読み直す (SYNC_PROTOCOL.md の `user.updated`。iOS・Android もこの版から読み直す)。
- サーバが古い (UserMe にキーが無い) ときは設定を出さず、既定のまま描く。

### 14.2 共通のカタログと規則 (`apps/shared/nav-items.json`)

- 項目: スレッド (threads)・アクティビティ (activity、Desktop / Web だけ)・Times (times-feed、スマホだけ)・下書き (drafts)・保存済み / 保存 (saved)・リマインダー (reminders)・ファイル (files)・キャンバス (canvases)・カレンダー (calendar)・タスク (tasks)・締切 (deadlines)・予約 (reservations、M112 で 3 クライアントとも描く。サーバが枠の一覧に答えるまで (M112 より前のサーバ) は出さない)。既定はすべて表示で、既定の順は Desktop (`desktop`) とスマホ (`mobile`) でそれぞれ今までどおり。
- 機能の状態で出入りする項目：在室状況 (attendance、M140) はワークスペースで有効なあいだだけ、操作 (actions、M143、docs/ACTIONS.md §9) は
  操作ボタンが有効で、押せるボタンが 1 つ以上あるあいだだけ (ゲストとボットは出ない) 実装済みに数える。どちらも両方の形 (`desktop`・`mobile`)
  にあり、スマホのタイルは在室状況の後ろ (数は出さない)。iOS は 2026-10-08 から「操作」のタイル (アイコン `bolt`)、Android は後の作業。
- 備品 (lending、M170〜M172、docs/LENDING.md §12.1) はワークスペースで備品が有効なあいだだけ (bootstrap の `lending` が null でない。
  ゲストとボットは出ない) 実装済みに数える。両方の形にあり、既定の順は予約の次。スマホのタイルの数は自分の延滞と、備品係なら
  `keeper_attention_count` を足したもので、1 以上のときだけ赤で出す。iOS は M171 (アイコン `shippingbox`)、Android は M172 (アイコン `Inventory2`)。
- `full(stored)`: `null` なら その形の既定の順と表示。そうでなければ 保存した順 (同じ key は最初の 1 つ、知らない key も残す)、続けて保存に無いカタログの項目を既定の順・既定の表示で。**新しい項目は保存済みの人には末尾に既定の表示で現れる。**
- `shown(full)`: カタログにあり・その形の項目で・そのクライアントが実装しているものだけを設定に並べ、表示のものを描く。知らない key と実装していない key (例: M111 の時点の reservations) は描かないが、保存のときは残す。
- 並べ替えは見えている項目だけ: それらが `full` で占めていた位置に新しい順で入れ、他 (別の形の項目・知らない key) はその場に残す。変更は `full` を丸ごと送り、「元に戻す」は `null`。
- Desktop vitest・iOS XCTest・Android JUnit が同じケースを通す。

### 14.3 形ごとの決め

- **順と表示は 1 つ**: パソコンで隠した「ファイル」はスマホのタイルでも隠れる (形ごとに別の設定にはしない。設定の説明にそう書く)。
- **Desktop / Web の広い画面（2026-10-12、§18）**：項目は場所のレールのアイコンかサイドバーの上の行。置き場所（アイコン列 /
  サイドバー / 表示しない）は `UserMe.desktop_places` で、`visible`（スマホのタイル）とは別（§18.2）。順はこの §14 のまま共通。
- **アクティビティ**: Desktop / Web のサイドバーの項目としてだけ隠せる。スマホは下のタブ、Android タブレットはレールのタブ、iPad はサイドバーの専用の行 (タブの代わり) で、どれも隠せない (未読の入口を消さないため)。
- **Times**: スマホのタイルだけ (Desktop / Web は Times のセクションの先頭の行のまま)。
- **操作** (actions、M143): スマホのタイルにも (`mobile`)。機能が有効で押せるボタンが 1 つ以上あるときだけ実装済みに数える (無ければタイルにも設定の行にも出ない)。Android は 2026-10-08 (ACTIONS.md §9.2)。
- **バッジ**: 動かしても数は付いたまま (スレッドの未読・赤、下書きの数、保存の数、リマインダーの通知済み)。Desktop の「下書き」「リマインダー」は 2026-10-12 から中身が無くても置いた所に出る（§18.2）。

### 14.4 設定の画面

- Desktop / Web：設定 → 表示 →「サイドバーの項目」。ドラッグか ↑ / ↓ で並べ替え、「元に戻す」。2026-10-12 から項目ごとの
  スイッチ（スマホのタイルの表示）の代わりに置き場所の選択（§18.2）。レールの「項目の配置」と「並べ替え…」（この画面を開く）からも。
  2026-10-13 からレールのアイコンとサイドバーの行をそのままドラッグしても並べ替えられる（同じ順、§18.2）。
- iOS: 自分 → 表示 →「ホームのタイル」。スイッチ、右上の「編集」で並べ替え (List の編集モード)、「元に戻す」。iPad のサイドバーのタイルも同じ。
- Android: 自分 → 表示 →「ホームのタイル」。スイッチ、「並べ替え」で ↑ / ↓ の行に、「元に戻す」(並べ替えのライブラリは足さない)。タブレットのホームの一覧も同じ。
- どれも変更をすぐ保存し、表示はすぐ変わる。サーバが断ったら元に戻して理由を出す。

## 15. 長いファイル名の省略 (2026-10-07)

長いファイル名は拡張子が見えるように、名前の途中を省略する（`研究報告書_最終版…2026年度.pdf`）。規則と例は全クライアント共通の
`apps/shared/file-name-ellipsis.json`（各クライアントの試験が同じ例を読む）。

- 拡張子：最後の `.` から後ろ。先頭（`.env`）・末尾（`notes.`）の `.` は除き、後ろは空白を含まない 1〜8 文字。全角の `．` は数えない。
- 拡張子があって本体が 12 コードポイントを超えるときは、本体の最後の 6 コードポイントを拡張子と一緒に残す（濁点の結合文字・
  絵文字の ZWJ 列・国旗などの途中では切らない）。拡張子が無ければ今まで通り末尾を省略する。
- Desktop / Web：`FileName`（前半だけが省略され、後半と拡張子は縮まない。`title` に全体）。iOS：`.truncationMode(.middle)`、
  Android：`TextOverflow.MiddleEllipsis`。作成欄の小さなタイルは 1 行目に本体、2 行目に拡張子（読み上げは 1 つの名前）。
- 文書のカードは 1 行（途中を省略）。メッセージのファイルの行など、もともと折り返して全体を出す所はそのまま。

## 16. 添付のダウンロードボタン（Desktop / Web、2026-10-07）

メッセージの写真・動画は、拡大表示を開かなくてもダウンロードできる（Slack と同じ）。

- 写真（1 枚の形のまま・2 枚以上の正方形の列）と動画のタイルの右上に小さなダウンロードボタン。マウス（またはペン）が
  タイルに乗っている間と、キーボードのフォーカスがタイルかボタンにある間（`:focus-visible`）だけ出す
  （`ui/Attachments.tsx` の `useDownloadReveal` / `DownloadOverlay`）。隠れている間はクリックを受けない。
- 押すと拡大表示のボタンと同じ `controller.downloadAttachment`（Tauri は「ダウンロード」フォルダへ保存（設定で
  毎回選べる）、Web は `<a download>`、どちらも認証つきの取得とトースト。PREVIEWS.md §9）。拡大表示は開かない
  （`stopPropagation`）。読み上げは「<名前> をダウンロード」、ツールチップは
  「ダウンロード」。
- ファイルの行は行全体がダウンロードなので、右端のアイコンを hover とキーボードのフォーカスで出す（読み上げは
  「<名前> をダウンロード」）。文書のカード（M108）はもともとダウンロードのボタンが常に見えている。
- 送信中・送信に失敗したメッセージ（`pending` / `failed`）には出さない。作成欄の送信前のタイル、キャンバス・ドキュメント
  の画像には付けない。検索結果のメッセージの行は行全体が 1 つのボタンなので付けない（ファイルの検索・一覧の行には
  もともとダウンロードがある）。スレッドは同じタイムラインなので同じ。
- タッチ（スマホの Web）：hover が無いので出さない（タッチの `pointerenter` は数えず、タップで付くフォーカスは
  `:focus-visible` でないので出ない）。ダウンロードは拡大表示のボタンから。iOS / Android のアプリは今まで通り。

## 18. 場所のレール（Desktop / Web の広い画面、2026-10-12）

利用者の要望：サイドバーの上にキャンバス・ドキュメント・予約・保存済み・在室状況・操作・カレンダー・タスク・下書き・
ファイルなどの項目が縦に並び、チャンネルがずっと下に押し出される。Slack のように、これらを細いアイコンの列にまとめる。

### 18.1 形

- サイドバーの列の左端に幅 52 px の**場所のレール**（`ui/PlacesRail.tsx`、読み上げは「場所」の `nav`）。ワークスペースの
  切り替え（上の行のワークスペース名、2 つ以上なら左端のワークスペースのレール）のすぐ下・右にあり、上から順に
  §14 の項目のアイコン（40 px の角丸、アイコン 20 px）、下端に「その他」（…）と「項目の配置」（つまみのアイコン）。どの項目を
  レールに置くかは §18.2（「スレッド」「下書き」は既定でサイドバーの行）。
- サイドバーの幅（ドラッグ・既定 260 px）はそのままで、レールの分だけ列が広い（`MainScreen` が `PLACES_RAIL_WIDTH` を
  足し、会話の欄の計算からは引く）。
- 名前はアイコンの右に出るツールチップ（ポインタを乗せたときとキーボードのフォーカスのとき。1 行目が名前と数、2 行目が
  その場所の説明。スレッドは ⌘+Shift+T も）。読み上げの名前は項目名（アクティビティは「アクティビティ（未読 3）」のまま）。
- 開いている場所は塗り（`bg-sidebar-active`、`aria-current="page"`）。バッジはアイコンの右上：スレッドの未読（メンションが
  あれば赤）、アクティビティ（同じ）、通知済みのリマインダー（赤）、予約のすぐできる作業（赤）。下書き・保存済みの数と
  在室の人数はツールチップと「その他」の行に出す（レールではうるさいので）。
- 未読のある場所のアイコンは濃い色（今までの行の太字に当たる）。

### 18.2 置き場所（アイコン列・サイドバー・表示しない）

利用者の要望（2026-10-12 の後半）：「スレッド」「下書き」はサイドバーの行のほうが使いやすい。項目ごとに置き場所を選びたい。
「リマインダー」がレールに出ず「その他」にしか無い。

- 項目ごとに **アイコン列**（レールのアイコン）・**サイドバー**（サイドバーの上の行）・**表示しない**（「その他」だけ）の 3 つから選ぶ。
  既定は「スレッド」「下書き」がサイドバー、ほかはアイコン列。どれを選んでも「その他」かサイドバーの「その他」から開ける。
- **アイコン列を隠す**スイッチ：切るとレールが無くなり、アイコン列の項目はサイドバーの行になる。サイドバーの行の最後に「その他」の行
  （表示しない項目、「アイコン列を表示」、「サイドバーの表示…」）が出る。
- **保存**：1 人に 1 つ `UserMe.desktop_places`（`users.desktop_places` jsonb、移行 0115）。`{rail: bool, items: [{key, place}]}`、
  `place` は `rail` / `sidebar` / `hidden`。`null` = 既定。`PATCH /users/me {desktop_places: {...} | null}` で丸ごと置き換え
  （64 個まで・key は nav_items と同じ形・重複は 422）。知らない key（新しいクライアントの項目）もそのまま残す。別の端末へは
  `user.updated` で揃う（Desktop / Web どうし）。サーバが古く `desktop_places` が無いときは既定で描き、置き場所の操作を出さない。
- **スマホのタイルとは別**：`nav_items` の `visible` はスマホのタイル（とスマホ幅の Web のホーム）だけのもの。パソコンで置き場所を
  変えてもスマホのタイルは変わらず、スマホで隠したタイルもパソコンには出る。2026-10-12 の前半だけ `visible` を「レールに出す」に
  使っていたが、それで隠した項目は既定（アイコン列）に戻る（引き継がない）。**順**は今までどおり `nav_items` の順で、スマホと共通。
- **中身が無いとき**：「下書き」「リマインダー」も置いた所に常に出す（前はレールでもサイドバーの行でも中身があるときだけ）。バッジは
  下書きの数（灰色）、リマインダーは通知済みの数（赤）か開いている数（灰色）。スマホのホームのタイルは今までどおり。
- レールの高さに入りきらない分は、順に後ろから「その他」に移る（`railFit`：1 つ 44 px、上下の余白 16 px、下の 2 つの
  ボタンの分を引く。窓の高さに ResizeObserver で付いていく）。隠れた項目にバッジがあれば「その他」に点（赤が勝つ）、
  開いている場所が隠れていれば「その他」が塗られる。サイドバーの行の項目は「その他」に入れない（見えているので）。
- **ドラッグで並べ替え**（2026-10-13、利用者の要望「左のアイコン一覧、ドラッグで位置を変えられるようにしたい。サイドバーの部分も」）：
  レールのアイコンを別のアイコンの上へドラッグすると、その前か後ろ（ポインタが上半分か下半分か）に動く。サイドバーの場所の行どうしも
  同じ。重なっている間は前後の隙間に線（`bg-accent-solid`）を出し、ドラッグ中の項目は薄くする。HTML5 のドラッグ（サイドバーの会話の
  行・タブと同じ。新しい依存は足さない）で、ブラウザはポインタが数 px 動くまでドラッグを始めないので、クリックはクリックのまま
  （ツールチップ・右クリックの「新しいタブで開く」・中クリック・⌘-クリック・キーボードもそのまま）。
  - **保存するのは `nav_items` の順**（§14、設定の「サイドバーの項目」と同じ 1 つの順、スマホと共通）。落とした項目が相手の項目の
    すぐ前か後ろに入り、ほかの項目（別の置き場所の項目・スマホだけの項目・知らない key）はその枠に残る（`navItemsAfterPlaceDrop`、
    `reorderNavItems` と同じ規則）。`desktop_places` は変わらない（`items` の並びに意味は無いまま）。設定の「元に戻す」が順も既定に戻す。
  - 動かせるのは同じ並びの中だけ（レールの中・サイドバーの行の中）。レールからサイドバーへ落としても何も起きない（置き場所は
    「項目の配置」か設定、アイコン・行の右クリック（§18.10）で変える）。「Times フィード」「自分の Times」は動かせず、落とす先にもならない（順は項目の後ろで固定、§18.5）。
  - サーバが古く `nav_items` が無いときはドラッグできない（既定の順のまま）。キーボードでの並べ替えは設定の ↑ / ↓ か、
    右クリックのメニューの「上へ」「下へ」（§18.10）。
- 「その他」のメニュー：レールに無い項目（入りきらない分と表示しない項目）を順に、アイコン・名前・バッジか数つきで。最後に
  「並べ替え…」（設定 → 表示 →「サイドバーの項目」を開く）。
- 「項目の配置」のメニュー（レールの下のつまみのアイコン）：項目ごとの行（アイコン・名前・今の置き場所）から入れ子で
  アイコン列 / サイドバー / 表示しない を選ぶ。変えるとすぐ保存。説明の 1 行、「アイコン列を隠す」、「並べ替え…」。
- **サイドバーの行**：⌘K（移動）と「未読」の行のすぐ下、セクションの上。前のサイドバーの項目の行と同じ見た目（アイコン 15 px、
  名前、右にバッジか数、未読があれば太字、開いている場所は塗り）。
- 設定 → 表示 →「サイドバーの項目」：一番上に「アイコン列を使う」スイッチ。項目ごとの行に置き場所の選択（アイコン列 / サイドバー /
  表示しない）とドラッグ・↑ / ↓ の並べ替え。表示のスイッチ（スマホのタイルの表示）はパソコンの設定から外した。「Times フィード」と
  「自分の Times」は置き場所だけ（順は項目の後ろ）。「元に戻す」は順を既定に戻し（スマホで隠したタイルは隠れたまま）、置き場所も既定に
  戻す（`desktop_places: null`。2026-10-12 の後半から Times の節の位置 `times_before` は残す、§18.9）。

### 18.3 キーボード

- レールはタブ 1 つ（開いている場所、なければ先頭）。↑ / ↓ で隣へ（端で反対の端へ回る）、Home / End で先頭・最後（「その他」と
  「レールに出す項目」も順に含む）。Enter / Space で開く。「その他」「レールに出す項目」の上の ↓ はメニューを開かずに次へ
  動く（キャプチャの段階で止める）。メニューは Enter / Space で開く。
- アイコンとサイドバーの場所の行の右クリックのメニュー（§18.10）は、フォーカスがあるとき Shift+F10 かコンテキストメニューのキーで開く。
- ⌘K（移動）、⌘+Shift+T（スレッド）、⌘+Shift+E・⌘+Shift+K、⌘1〜⌘9 など今までのショートカットはそのまま（タブが 2 つ以上のときの ⌘1〜⌘9 は §19.4）。

## 19. タブ（Desktop / Web の広い画面、2026-10-12）

利用者の要望：ブラウザのように上にタブを並べ、チャンネル・DM・スレッド・ドキュメントのページ・場所を別のタブに開いておきたい。

### 19.1 形

- タブが 2 つ以上のとき、上の行（履歴の ← → と検索）のすぐ下、会話の欄とスレッドの欄の上に**タブの列**（`ui/DesktopTabBar.tsx`、
  高さ 36 px、サイドバーと同じ色）。タブが 1 つなら列は出ず、見た目は今までと同じ。サイドバーと場所のレールはタブに関係なく 1 つで、
  列の分だけ縦に伸びる（`.desk-tabs-on`）。
- タブは幅 200 px（狭いと 104 px まで縮み、それでも入らなければ横にスクロール。`useScrollRow` で端がぼける）。中身は
  アイコン・名前・未読・閉じる ×。開いているタブは会話と同じ地の色で枠つき、下の線を隠して会話とつながる（ダークでも見分けられる）。
- **名前とアイコン**：チャンネルは名前（# / 鍵）、DM は相手の名前とアイコン（グループ DM は名前の並び）、場所はその名前とレールの
  アイコン（スレッド・アクティビティ・カレンダー…）、ドキュメントはページの題（無ければ「ドキュメント」）、検索は「検索：語」。
  スレッドを開いたタブもその会話の名前。
- **未読**：後ろのタブだけ。会話はサイドバーの行と同じ規則（`hasUnread`。メンション・DM は赤い数、ほかは点）、スレッドと
  アクティビティはレールと同じバッジ。開いているタブには出さない（読んでいるところなので）。
- 列の右端の ＋ は ⌘T と同じ：「移動・検索」（⌘K の画面。入力欄は「新しいタブで開く：…」）が開くだけで、まだタブは作らない。
  会話（チャンネル・DM）かキャンバスを選ぶと、それが新しいタブ（今のタブのすぐ右）になって前に出る。Esc・外のクリックで
  閉じると何も作らない（2026-10-12 の利用者の要望。前は今のタブを複製してから ⌘K を開いていた）。

### 19.2 開く・閉じる・並べ替え

- **新しいタブで開く**：サイドバーの会話の行・場所のレールのアイコンとサイドバーの場所の行・「スレッド」のカード・ドキュメントの
  木の行（題と ⋯ のメニュー）の右クリックのメニューの「新しいタブで開く」、中クリック、⌘+クリック（Windows は Ctrl+クリック）。
  どれも今のタブのすぐ右に開く。前に出すか後ろに置くかの規則（2026-10-12 の利用者の要望で変えた）：
  - 右クリックのメニューの「新しいタブで開く」と ⌘+クリック（Ctrl+クリック）は**前に出す**（新しいタブに切り替わる）。
  - 中クリックはブラウザと同じく**後ろに**開き、今の画面はそのまま（ホイールで続けて開いておく使い方のため）。
  - Shift を足すと逆になる：⌘+Shift+クリックは後ろ、中クリック + Shift は前。
  - ふつうのクリックは今までどおり今のタブの中で移る。
- スレッドのカードから開いたタブは、その会話とスレッドの欄。場所のアイコンから開いたタブは、その場所（「自分の Times」は自分の
  times の会話）。
- **閉じる**：×、タブの中クリック、⌘W、タブのメニューの「タブを閉じる」、タブにフォーカスがあるとき Delete / Backspace。
  開いているタブを閉じると右隣（無ければ左隣）が前に出る。最後の 1 つは閉じない（⌘W は今までどおりウィンドウを閉じる）。
  「他のタブを閉じる」もある。
- **並べ替え**：ドラッグ（落とした所の左半分なら前、右半分なら後ろ）、タブのメニューの「左へ移動」「右へ移動」（キーボードでも
  Shift+F10 で開ける）。
- タブは 20 個まで（超えると「タブは 20 個までです」）。

### 19.3 タブごとに覚えること・エンジン

- タブごとに：中央の表示（会話・場所・検索・ドキュメントのページ）、スレッドの欄、会話のタブ（メッセージ / キャンバス / 予定 /
  タスク）、← → の履歴（M67 の場所の履歴をタブごとに 1 本）、メッセージに飛んだ位置（`messageFocus`）。
- 開いているタブの状態が画面の状態そのもので、ほかのタブはその写し（`TabSnapshot`）。切り替えると写しを画面に戻す。会話の
  スクロール位置は今までのスクロールの記憶（M75、`scrollMemory`、場所ごと）で戻り、場所の一覧（スレッド・保存済み・検索結果…）も
  ← → で戻ったときと同じく元の位置に戻る（`restoreView`）。下書きは会話ごとなのでタブに関係なく残る。スレッドの欄の中の
  スクロール位置は覚えない。
- **エンジンが開く会話は開いているタブの会話だけ**（`openChannel` / `closeChannel` は 1 つだけ。SYNC_PROTOCOL.md §10：画面に出た
  ものだけを既読にする）。後ろのタブはタイムラインを描かないので、既読・入力中・閲覧中のどれも送らない。未読の数はストアの値を
  そのまま出す。切り替えると、その会話が開いて今までどおり画面に出た行から既読になる。
- 通知・パーマリンク・検索結果・⌘K など、ほかの所からの移動は開いているタブの中で起きる（ブラウザでリンクを開くのと同じ）。
- Web の戻る / 進む（ブラウザの履歴）：別のタブに切り替えたことも 1 つの履歴になり、戻るとそのタブ（まだ開いていれば）に戻る。

### 19.4 キー

| 操作 | デスクトップ版 | Web（ブラウザが ⌘T などを使うため） |
| --- | --- | --- |
| 新しいタブ（「移動・検索」が開き、選んだものが新しいタブで前に出る。Esc なら何も作らない） | ⌘T（Ctrl+T） | ⌥T（Alt+T） |
| タブを閉じる | ⌘W（Ctrl+W） | ⌥W（Alt+W） |
| 前 / 次のタブ（端で回る） | ⌘⇧[ / ⌘⇧]、Ctrl+Shift+Tab / Ctrl+Tab | ⌥⇧[ / ⌥⇧] |
| n 番目のタブ（9 は最後） | ⌘1〜⌘9（Ctrl+1〜9） | ⌥1〜⌥9（Alt+1〜9） |

- ⌥ のキーは文字ではなく物理キー（`event.code`）で見る（Mac の ⌥ は別の文字を打つため）。日本語入力の変換中は何もしない。
  ダイアログや ⌘K が上にあるときは何もしない（タブが 2 つ以上なら ⌘W がウィンドウを閉じないよう止める）。
- **⌘1〜⌘9 とワークスペース**：今まで ⌘1〜⌘9 はワークスペースの切り替え（M16c）。タブが 2 つ以上のときはタブに使い、
  ワークスペースは ⌘⌥1〜⌘⌥9（Ctrl+Alt+1〜9）で。タブが 1 つなら ⌘1〜⌘9 は今までどおりワークスペース。⌘⌥ はいつでも使える。
- タブの列は WAI-ARIA の tablist（読み上げは「タブ」）。Tab で開いているタブに入り、← / → / Home / End で隣のタブへ移って開く
  （`useScrollRow`）。× は Tab で止まらない（Delete・メニュー・⌘W で閉じられるため）。キーの一覧（⌘/）に「タブ」の節。
- デスクトップ版（Tauri）の中クリックは、ウィンドウ全体で mousedown / auxclick の既定の動作を止める（リンクの中クリックで
  webview が新しいウィンドウを開かない・Windows の自動スクロールが始まらない）。
- 確かめていないこと：macOS のデスクトップ版で ⌘W がメニューの「ウィンドウを閉じる」より先にページに届くこと（WKWebView は
  キーをページに先に渡し、ページが止めたものはメニューに回さないはずだが、Tauri のビルドでは試していない）。

### 19.5 保存（この端末だけ）

- 開いているタブは `localStorage` の `chikuwa.tabs.<サーバ>|<ユーザー名>`（アカウントごと）に、id と行き先だけ（表示・会話・
  スレッド・ページ・ファイルの範囲・会話のタブ・検索の語。本文は入れない）。タブが 1 つのときは消す。読めないとき（プライベート
  ウィンドウなど）はタブを使えるが次の起動に残らない。履歴（← →）とメッセージの位置は残さない。
- 次の起動で戻す。行き先がもう無いタブは捨てる：会話がストアに無いか読めない（退出・外された・削除・非公開化）、知らない表示、
  ドキュメントのページが木に無い（木を読んだ後）。スレッドやファイルの範囲の会話だけが無ければその表示に戻す。開いていたタブが
  捨てられたら右隣（無ければ左）を開く。動いている間に後ろのタブの行き先が無くなっても同じく閉じる。
- デスクトップ版はキャッシュがあるので画面を出すときに戻す。ブラウザはストアが空で始まるので、最初の bootstrap が入ってから戻す
  （それまでは保存もしない）。ブラウザでリンク（/m/・/c/・/p/）から開いたときは、戻したタブの後ろにリンクの画面をもう 1 つの
  タブとして足して前に出す。
- 設定 → 表示 →「**タブを使う**」（この端末だけ、既定はオン）。切ると開いているタブだけが残り、列・「新しいタブで開く」・タブの
  キーが無くなる（⌘1〜⌘9 はワークスペースに戻る）。

### 19.6 狭い画面（スマホ幅の Web）

- タブの列は出さない（下のタブと各タブの画面の積み重ねのまま、§5）。窓を狭めても広い画面のタブは消えず、広げると戻る。
- 会話・場所には自分の URL が無い（「リンクをコピー」も最新のメッセージのリンク、§18.7）ので、「新しいタブで開く」は出さない。
  ドキュメントのページだけは `/p/<id>` があるので、木の行の「新しいタブで開く」はブラウザの新しいタブでそのページを開く。

### 19.7 試験

- vitest `tests/desktopTabs.test.tsx`（本物の MainScreen・SyncEngine・偽サーバ）：タブ 1 つで列が無いこと、行の右クリックの
  「新しいタブで開く」（前に出す）、中クリック（後ろ・未読の点）・⌘+クリック（前）・⌘⇧+クリック（後ろ）・ふつうのクリック、
  ⌘T と ＋（「移動・検索」が開くだけ・Esc で何も作らない・選んだものが新しいタブで前に出る・その後の ⌘K は今のタブの中で移る）、後ろのタブは
  エンジンが開かず既読を送らないこと・切り替えると開くこと、タブごとの表示・スレッドの欄・← → の履歴・場所の一覧の
  スクロール位置の復元、× とタブの中クリックで閉じる・右隣が前に出る・最後の 1 つ、ドラッグとメニューの並べ替え、キー
  （⌘T・⌘W・⌘⇧[ ]・Ctrl+Tab・⌘1 / ⌘9、タブ 1 つのときの ⌘W・⌘1）、保存と復元・無くなった会話のタブを捨てる、ブラウザの
  起動（bootstrap の後に戻す）、「タブを使う」を切ったとき、スマホ幅、レールの場所と「スレッド」のカードのメニュー。純粋な規則
  （挿入・隣・移動・回る・⌘9・キーの対応・保存の読み書きと復元）も同じファイル。

## 20. 他のアプリから共有して送る（Android、2026-10-12）

利用者の要望：ほかのアプリの「共有」から、ファイル・画像・動画・PDF・文章・リンクを Taylis の会話に送りたい。
（iOS は Share Extension で別に作る。ここは Android の決め。）

### 20.1 受け口（`share/ShareActivity.kt`）

- 共有だけを受ける `ShareActivity`（メインの画面とは別のアクティビティ）。インテントフィルタは `ACTION_SEND` と
  `ACTION_SEND_MULTIPLE`、型は `*/*`（ファイル・画像・動画・PDF に加えて `text/plain` の文章と URL も入る）。
- インテントから読むもの（`ShareActivity.read` → `SharePayload.parse`、純粋な規則）：
  - `EXTRA_STREAM`（1 つ、または一覧）の URI（`ClipData` は見ない。Chrome はリンクの共有で共有シートのプレビューの画像をそこに入れるため）。**`content://` で、ほかのアプリのものだけ**を読む。`file://` と、
    このアプリ自身のプロバイダ（`<パッケージ>.files` など、マニフェストに載るものすべて）の URI は読まない（悪いアプリが
    `file:///data/data/jp.chikuwachat.android/…` を共有させると、このアプリのデータベースやトークンがサーバに送られてしまうため）。
    断ったものは数だけ「共有できない項目が n 件あります」と出す。
    - 判定は URI の文字列ではなく、Android の `Uri` が解析した scheme と**復号済みの authority**（`ContentResolver` が
      プロバイダを探すのと同じもの）で行う（REVIEW-v0.1.62 #2）。`content://jp%2Echikuwachat%2Eandroid%2Efiles/…` のような
      パーセント符号化、`10@…` のユーザー ID の接頭辞、大文字小文字の違いも自分のプロバイダとして断る。名前の一覧に無い別名も、
      `PackageManager.resolveContentProvider` がこのアプリのパッケージ（または同じ uid）に解決するなら断る（問い合わせに
      失敗したときも読まない）。
  - `EXTRA_TEXT` は本文の初めの文。件名（`EXTRA_SUBJECT`、ブラウザならページの題）は、ファイルが無く、文に含まれていない
    ときだけ前の行に足す（Chrome のリンクは「題\nURL」になる）。メールのファイルの件名は入れない。
  - Direct Share で選ばれたときの `EXTRA_SHORTCUT_ID`（§20.5）。
- サインインしていない（ワークスペースが無い・サインアウトした）ときは、上に「サインインすると共有を続けられます」と × を出し、
  その下にアプリのサインイン画面（`AppRoot`）をそのまま出す。サインインが終わると同じ画面が共有の画面に変わる（共有の中身は
  `ViewModel` が持っているので失わない）。Google サインイン（M48）はブラウザから `MainActivity` に戻るので、そのときは最近使った
  アプリから共有の画面に戻る。

### 20.2 画面（`ShareScreen`、ライト / ダーク、日本語・英語・中国語）

- 上のバー：×（キャンセル）・「共有」・「送信」。送信は、送信先を選び、下の問題が無いときだけ押せる。
- ワークスペースが 2 つ以上なら一番上にワークスペースの切り替え（タイルと名前、押すと一覧）。選ぶとアプリの画面のワーク
  スペースも切り替わる（アプリが出すワークスペースは 1 つ、WORKSPACES.md §5.2）。サインアウトしているものを選ぶとそのサイン
  イン画面になる。
- 共有するもの：ファイルごとに横に並ぶカード（画像・動画はサムネイル（Android 10 以上は `loadThumbnail`、それより前は画像だけ
  縮小して読む）、ほかは PDF・動画・ファイルのアイコン、名前（長いと真ん中を省略、§15）と大きさ）。文章だけの共有はカードが無く、
  文はメッセージの欄に入っている。
- 問題（赤い字、送信できない）：添付の数（`limits.max_attachments_per_message`、10）を超える・大きさの上限
  （`limits.max_attachment_bytes`）を超える（「「a.mp4」は大きすぎます（上限 100.0 MB）」）・空のファイル・読めないファイル・
  メッセージの長さ（`limits.max_message_length`）を超える・送るものが無い。コンポーザと同じ上限で、サーバも同じく確かめる。
  型はサーバが中身から決める（SECURITY.md §4）ので、ここでは断らない。
- メッセージ（任意）の欄：共有された文が初めから入っていて、書き直せる。
- 送信先：「送信先：#general」の行、「会話を検索」の欄、その下に一覧。何も打っていないときは「最近」（共有で送った会話、
  次に「移動・検索」の最近の会話（§6.2）、8 件まで）と「すべての会話」（新しいメッセージの順、同じなら名前）。打つと
  「移動・検索」と同じ一致の規則（`apps/shared/jump-match.json`）で、チャンネルの名前と DM の相手の名前・ユーザー名から探す。
  出すのは**自分が入っている、アーカイブされていない、投稿できる**会話だけ（告知チャンネルはオーナーと管理者だけ、M15a）
  （`ShareDestinations`）。まだ DM の無い人・入っていない公開チャンネルは出さない（先にアプリで会話を始める）。

### 20.3 ファイルを読むこと（コピーする）

- 共有でもらう読み取りの許可は共有の画面が開いている間だけで、`takePersistableUriPermission` はシステムのファイル選択で
  選んだ文書にしか使えない。そこで**画面が開いたらすぐ**、各ファイルをアプリの中（`filesDir/share/<共有の id>/<番号>`）に
  コピーする（`ShareModel`、回転しても続く）。大きさの上限を超えると分かっているものはコピーしない。大きさを言わない
  プロバイダのものは、コピーしながら上限を超えたところで止め、「大きすぎます」にする。
- 「送信」はコピーが終わるのを待ってから（その間バーに回るしるし）ジョブを残して画面を閉じ、「送信を始めました。終わると通知で
  お知らせします」と出す。キャンセルや送らずに閉じたときはコピーを消す。消し損ねたもの（ジョブの無いフォルダ）は 1 日経つと
  次の共有のときに消す。
- 実際に読むところ（大きさと名前の問い合わせ・コピー・サムネイル）は、どれも同じ文字列を `Uri` にしたものを**その場で
  もう 1 度**同じ規則で確かめてから読む（`ShareModel.foreign`）。確かめた URI と読む URI の解釈がずれることはない。

### 20.4 送信（`share/ShareWorker.kt`、`ShareJob.kt`）

- ジョブ（`job.json`：ワークスペース・会話・本文・**冪等キー**（`client_msg_id`、ここで 1 度だけ作る）・ファイルとその添付 id）を
  コピーの横に書き、WorkManager の `ShareWorker` に渡す（`enqueueUniqueWork("share:<id>")`）。ネットワークがあるときに走り、
  急ぎ（expedited、枠が無ければふつうの仕事）。アップロードするものがある間は**フォアグラウンドの仕事**（`dataSync`）になり、
  進み具合の通知（％、音なし、チャンネル「共有の送信中」）を出す。画面を閉じても、アプリを閉じても続く。
- `ShareSender`（純粋な手順）：添付 id の無いファイルを 1 つずつ `POST /attachments`（コンポーザと同じ道、同じ検査）。id は
  もらうたびにジョブに書くので、やり直しは残りだけを上げる。全部上がったら `POST /channels/{id}/messages` で**本文と全部の添付を
  1 つのメッセージ**にして送る。冪等キーが同じなので、送った後に答えが失われてやり直しても、サーバは初めのメッセージを返す
  （二重にならない、SYNC_PROTOCOL.md §9）。
- 失敗：ネットワーク・429・5xx は WorkManager のやり直し（30 秒から倍々、ネットワークが戻るのを待つ。その間の通知は「接続が
  戻ったら送信します」）。12 回で諦める。4xx（入っていない・上限など）とサインアウト（リフレッシュが断られた 401）とコピーが
  消えたときはそこで終わる。サーバが添付を受け取らない（`attachment_invalid`：使われないまま 24 時間で消えた）ときは 1 度だけ
  上げ直す。
- API の呼び出しはアプリと**同じ** `ApiClient`（`AppController.shareClient`。ワークスペースごとに 1 つ）。別に作るとリフレッシュ
  トークンの回転が 2 か所で起き、使い回しと見なされるため（SECURITY.md §2.3）。
- **ジョブは共有したアカウントのもの**（REVIEW-v0.1.62 #1）：ジョブにはサーバの URL に加えて、共有した人の**ユーザー ID**
  （変わらないもの）と**サインインの id**（`Workspace.session`、サインインのたびに新しく作る）を書く。仕事は、そのサーバに
  今サインインしているのが同じユーザーの同じサインインのときだけ、そのアカウントのクライアントで送る（`ShareJob.accountIn`）。
  違えば（サインアウトした・同じサーバに別の人がサインインした・サインインし直した・古い版のジョブで ID が無い）、どの
  アカウントの名前でも 1 つも送らずに捨てる。送る途中も、各アップロード・投稿の前と答えの後に同じことを確かめ
  （`AppController.shareStillOurs`。クライアントがサインアウトや新しいサインインで替わっていないことも見る）、変わっていれば
  そこで止める。
- **サインアウトで消す**：サインアウト（自分で・サーバに切られた）、一覧から外す、同じサーバに別のアカウントでサインイン
  したときは、そのアカウントの保留中のジョブとコピーを消し、その WorkManager の仕事（ジョブごとの `share:<id>` と
  ワークスペースごとのタグ `share-server:<サーバ>`）を取り消し、共有の通知（送信中・待ち・結果。通知にワークスペースを
  書いておく）も消す（`ShareWorker.dropAccount`）。走り出していた仕事が後から書き戻すことはない（`ShareJobs.update` は
  ジョブが残っているときだけ書く）。サーバにセッションを切られたときだけ、各ジョブに「送信できませんでした」を 1 度出す。
- 終わったら：送れたときは「#general に送信しました」（押すとその会話を開く、10 分で消える）、送れなかった
  ときは「#general に送信できませんでした」と理由（押すと会話を開く）。チャンネルは「共有の送信結果」。画面に出ている
  ワークスペースならメッセージをすぐストアに入れる（自分の投稿と同じく既読も進む）。ジョブとコピーは消す。通知の許可が無い
  ときは通知を出さないだけで、送信は同じ。

### 20.5 Direct Share（共有シートに会話を出す）

- `res/xml/shortcuts.xml` の `share-target`（カテゴリ `jp.chikuwachat.android.category.SHARE_TARGET`、`*/*`、`ShareActivity`）。
  会話のショートカット（メッセージの通知が会話ごとに作るもの、PUSH_NOTIFICATIONS.md §16）にこのカテゴリをつけたので、共有
  シートの上の段に最近の会話が出る。共有で送った会話にも、ショートカットが無ければ作る（通知のものがあればそのまま）。
- 選ばれると `EXTRA_SHORTCUT_ID`（`conv:<ワークスペースの要約>:<会話の id>`）から、ワークスペースを切り替え、その会話を選んだ
  状態で開く（`ShareDestinations.shortcutTarget`）。送信はふつうどおり「送信」を押す。サインアウトでショートカットが消えるのは
  今までどおり。

### 20.6 試験

- JVM `ShareTest`：インテント → 項目（1 つ・複数・重複・`file://` とこのアプリのプロバイダを断る・リンクと題・件名の扱い・
  文章が複数・共有でないインテント・Direct Share の id）、ファイル名、上限の言葉、送信先（投稿できる会話だけ・最近が先・
  新しい順・検索・ショートカットからワークスペースと会話）、送信（全部上げて 1 つのメッセージ、id を 1 つずつ残す、やり直しは
  残りだけ・答えが失われても同じキーで 1 つだけ、一時的な失敗と断られたとき、`attachment_invalid` の上げ直しは 1 度）、
  ジョブの保存と片付け。REVIEW-v0.1.62：符号化・ユーザー ID 付き・大小文字の違う authority、システムが自分に解決する
  別名を断り、ほかのアプリの URI は通すこと（#2）。A の共有を（本文だけ・未アップロード・アップロード済みで）B のサインイン後に
  再開しても、B のクライアントにも A のクライアントにも 1 つも要求を送らないこと、アップロードの途中・やり直し待ち・投稿中に
  アカウントが替わると止まること、サインアウトでそのアカウントのジョブとコピーが消え、別のサーバ・残すアカウントのものは
  残ること、消した後に書き戻さないこと（#1）。
- エミュレータ（ChikuwaChat_Pixel_9、API 36、開発サーバ）：ファイルアプリの Downloads から PDF を共有 → 共有シートに Taylis →
  サムネイル・名前・大きさ・メッセージを書いて #ai-test に送信 → 添付 1 つとメッセージ 1 つ、「#ai-test に送信しました」の通知。
  Chrome のメニューの「共有…」→ 共有シートの上の段に #ai-test（Direct Share）が出て、選ぶとその会話を選んだ状態で開く。
  アプリのアイコンから開いて #fname-check に送ると「Example Domain\nhttps://example.com/」のメッセージになり、通知を押すと
  その会話が開く。キャンセルするとコピーが消える。
- 見つけて直したこと：Chrome はリンクの共有でも `ClipData` に共有シートのプレビューの画像（ファビコン）を入れるので、それを
  ファイルとして拾っていた（§20.1 で `ClipData` を見ないことにした）。

## 21. iOS の共有拡張（Share Extension、2026-10-12）

ほかのアプリ（ファイル・写真・GoodNotes・Safari など）の共有シートから「Taylis」を選ぶと、ファイル・写真・動画・PDF・文章・
リンクを会話に送れる。拡張機能 `ShareExtension`（バンドル ID `jp.chikuwachat.ios.ShareExtension`、アプリに埋め込み、版と
ビルド番号はアプリと同じ）。Android の共有先は別の節。

### 21.1 受け付けるもの

- 有効化の規則（`NSExtensionActivationRule`）：ファイル・画像・動画はそれぞれ 10 件まで（1 メッセージの添付の上限、SECURITY.md §4）、
  Web の URL・Web ページは 1 件、文章。型は問わない（サーバが先頭バイトで判定する）。
- `NSItemProvider` ごとに：ファイルでないリンク（Safari のページなど）と文章はメッセージの本文に入れる（改行でつなぐ。送る前に
  直せる）。それ以外はファイルとして、システムが渡すファイル表現（`loadFileRepresentation`）を App Group の共有のフォルダに
  そのまま複写する（ディスクからディスクへ。メモリに丸ごと読まない：拡張機能のメモリ上限 約 120 MB）。メモリ上の画像しか
  渡さないアプリの画像だけは JPEG にして書く。名前は渡されたファイル名（無ければ型の拡張子を付ける）。読めなかった項目は
  件数を出す。

### 21.2 画面

- SwiftUI のシート 1 枚（ライト・ダークはシステムに従う。言語はアプリで選んだ言語 → 端末の言語の順で、日本語・英語・簡体字中国語。
  文言は `ShareExtension/Localizable.xcstrings`、サーバのエラーの文は `ErrorMessages.swift` を共有）。上に「キャンセル」と「送信」。
- **ワークスペース**：サインインしているワークスペースが 2 つ以上なら選ぶ（最初はアプリで開いていたもの）。
- **送信先**：最近の会話（アプリが背面に回るときに App Group に残す、開いているワークスペースの参加中の会話。新しい投稿の順、
  30 件）と検索。検索は初回に `GET /channels`・`GET /users`・`GET /users/me` で参加中の会話をすべて読み、名前（「#」を除く）と
  DM の相手のユーザー名を、大文字小文字・全角半角を区別せずに語ごとに絞る（名前が語で始まるものが先）。アーカイブ済みと、
  投稿できないアナウンスチャンネル（オーナーと管理者以外）は出さない。スレッドへの返信は今は無い（トップレベルの投稿だけ）。
- **添付するファイル**：縮小画像（QuickLook がファイルから作る）・名前・大きさ・外すボタン。サーバの上限（bootstrap の
  `limits`、アプリが App Group に残す。無ければ 100 MB・10 件）を超えるファイルには「大きすぎます（上限 …）」を出し、送信できない。
- **メッセージ**：任意の本文（共有された文章・リンクが入っている）。
- **サインインしていない**（アプリにワークスペースが無い、またはアプリがまだ新しい版で一度も起動していない）：「Taylis を開いて
  サインインしてください」と閉じるだけ。

### 21.3 認証の共有

- トークンは Keychain だけに置く（SECURITY.md §2.3）。アプリと拡張機能が共有する Keychain のグループ
  `<チーム ID>.jp.chikuwachat.ios.shared`（`keychain-access-groups`、Info.plist の `TaylisKeychainGroup`）に、ワークスペースごとの
  refresh token（アカウント `サーバ|ユーザー名`）と、今の access token と期限（`サーバ|ユーザー名#access`）。UserDefaults や
  ファイルには置かない。
- **移行**：前の版はアプリだけのグループに refresh token を置いていた。アプリは起動のたびに（Keychain を読む前に）サービス
  `jp.chikuwachat.ios` の項目を共有のグループへ移す（`SecItemUpdate` で `kSecAttrAccessGroup` を変える。値はそのままなので
  誰もサインアウトしない。移すものが無ければ何もしない）。新しい項目は最初から共有のグループに作る。署名にグループが無い
  ビルドではアプリのグループのまま動く。
- **ローテーションの競合**：refresh token は使うたびに替わり、替わった古いトークンを 30 秒の猶予の後に使うとセッションごと
  失効する。そこで refresh は App Group のファイルロック（`Locks/tokens.lock`、`flock`。プロセスが終われば外れる）を持っている
  間だけ行い、そのとき Keychain にある refresh token から始める（アプリの `ApiClient.refresh` も、相手が替えていれば Keychain の
  新しい方を使う）。拡張機能はふだん Keychain の access token をそのまま使い、期限切れ（あと 60 秒未満）か 401 `token_expired`
  のときだけロックを取る。ロックの中で、相手がもう新しい access token を置いていればそれを使い、無ければ refresh する。
  refresh が 401 なら「サインインし直す」扱い（Keychain は消さない。アプリが次に気付いてそのワークスペースだけサインアウトする）。
- **セッションの世代（2026-10-14、REVIEW-v0.1.62 #4）**：サインアウトしたあとに届いた拡張機能の refresh の応答が、消した
  トークンを Keychain に書き戻していた（再ログイン後なら新しいセッションのトークンを上書きした）。そこでアカウントごとに
  「世代」（整数）とサインイン中かどうかを App Group のファイル `Auth/sessions.json` に持つ（秘密は無い。`AccountSessions`）。
  - アプリはサインイン（ログイン・招待・Google）のたびに世代を 1 つ上げてからトークンを保存し、サインアウト・削除・同じ
    サーバの別アカウントへの入れ替えのたびに世代を上げて「サインアウト」と記録してからトークンを消す。どちらも
    セッションのロック（`Locks/sessions.lock`）の中で 1 つの手順として行う。
  - 拡張機能の `ShareApi` は作られたときの世代を覚え、トークンを使う前に「世代が同じでサインイン中」かを確かめる（違えば
    「サインインし直す」扱いで何も送らない）。refresh の応答は同じロックの中でもう一度確かめてから保存し、違えば捨てる。
    アプリの `ApiClient` も refresh の結果を同じ確かめ方で保存する（アプリ自身の `sessionVersion` の確認はそのまま。古い
    クライアントの応答は保存せずにそのクライアントをサインアウトさせる）。
  - セッションのロックはファイルの書き込みと Keychain の操作の間だけ持つ（数ミリ秒。通信の間は持たない）。トークンのロックは
    refresh の通信の間ずっと持つので、サインアウトがそれを待たないように別にした。順序はいつもトークンのロック → セッションの
    ロック。2 秒で取れなければロックなしで進む（止まった拡張機能がアプリのサインアウトを止めないため）。
  - 記録の無いアカウント（この版より前から使っている端末）は世代 0、Keychain に refresh token があればサインイン中とみなす。
  - 保留中の共有は、シートを開いたときの世代を `share.json` に持つ。送る前（アップロードの前と投稿の前）に世代が変わって
    いたら、送らずに失敗として消す（アプリが「送信できませんでした」と知らせる）。前の版の共有（世代なし）は世代 0。
- **ロックとサスペンド（2026-10-14、TestFlight build 115 / 119 の `RUNNINGBOARD 0xdead10cc`）**：iOS は App Group のファイルに
  ロック（`flock`）を持ったままサスペンドされたプロセスを強制終了する。アプリが refresh の通信中（トークンのロックを持ったまま）
  に背面へ回り、そのままサスペンドされて落ちていた。そこで App Group のロック（`tokens.lock`、`sessions.lock`、共有の
  `claim.lock`）はすべて `FileLock` を通し、持っている間はバックグラウンドの実行時間を確保する（アプリは
  `UIApplication.beginBackgroundTask`、拡張機能は `ProcessInfo.performExpiringActivity`）。
  - 時間が切れる（期限切れの通知が来る）と、その場でロックを外して閉じる（`isHeld` が偽になる）。時間をもらえないとき
    （残りが無い）はロックを取らない（タイムアウトと同じく「ロックなし」で進む）。待つ側はロックを取るまで何も持たない。
  - refresh は通信の途中でロックを失っても、届いた応答は「Keychain の refresh token が送ったものと同じとき」だけ保存する
    （セッションのロックの中で確かめて保存する）。違えば別のプロセスが先に refresh したので、応答は捨てて保存済みの新しい方を
    使う。ロックを失った後は再試行しない（同じトークンで別のプロセスが refresh しているかもしれないため）。
  - 共有の `claim.lock` はアップロード中に時間が切れれば外れる。アップロードはシステムが続け、終わってアプリが起こされた
    とき（または次の起動・前面復帰で）取り直す。
  - 背面に回るときの App Group への書き込み（共有シートの一覧、ウィジェットのスナップショット）とキャンバス・Wiki の保存も
    1 つのバックグラウンドタスクの中で行い、終わったら終える。

### 21.4 送信と保留（pending shares）

- 「送信」でまず共有を App Group の `PendingShares/<id>/` に保存する：`share.json`（ワークスペース、会話、本文、
  `client_msg_id`、ファイルごとの名前・型・大きさ・multipart の境界・アップロード後の添付 id）と `files/`（複写）。
  シートが開いている間はフォルダの `claim.lock` を持ち、送る人（拡張機能かアプリ）もその間だけ持つので、同じ共有を 2 つの
  プロセスが同時に送らない。
- 各ファイルはアプリと同じ `POST /attachments`（multipart、同じ `Multipart` のコード）で上げる。本文はファイルとして
  `body-<n>` に書き（1 MB ずつ）、共有ごとのバックグラウンドの URLSession（`jp.chikuwachat.ios.share.<id>`、
  `sharedContainerIdentifier` = App Group）でアップロードする。全部上がったら `POST /channels/{id}/messages` を 1 回、本文・
  添付 id・共有を作ったときに決めた `client_msg_id` で送る。同じ `client_msg_id` の再送は既にあるメッセージを返すので、
  誰が何度送っても投稿は 1 つ。
- シートは進み具合を出して待ち、投稿できたら閉じる。大きなファイルで待てないときは「閉じる（送信は続きます）」：アップロードは
  システムの中で続き、共有はアプリに任せる。終わったときに拡張機能がもういなければ iOS がアプリを背面で起こし
  （`handleEventsForBackgroundURLSession`）、アプリは同じセッションにつないで結果を受け取り、投稿してから眠る。
- **確実さのための選択**：アップロードの結果を受け取れなかった場合も含め、アプリは起動のたびと前面に戻るたびに残っている共有を
  すべて送り直す（上がっていない分だけ上げ、投稿する）。共有をファイルに残し、投稿が冪等なので、拡張機能が途中で終わっても、
  通知が来なくても、二重に投稿せずにいつか届く。
- **失敗**：
  - 通信できない・サーバの一時的なエラー（429・5xx）：保留。シートは「今は送信できませんでした。Taylis を開いたときにもう一度
    送信します」。
  - access token の期限切れ（401）：一度だけ refresh して上げ直す。refresh も断られたら保留（サインインし直すと送る）。
  - サーバが断った（大きすぎる `attachment_too_large`、`image_too_large`、空のファイル、会話に書けない 403 など）：共有を消して
    その理由（サーバのエラーの文）を出す。アプリが送っていて断られたときは「「#…」への共有を送信できませんでした：理由」を
    知らせる。
  - 投稿が `attachment_invalid`（上げてから 24 時間を過ぎ、サーバが未使用の添付を消した）：一度だけ全部上げ直す。
  - 7 日たっても送れない共有はアプリが消して知らせる。share.json の無いフォルダ（送信の前に終わったシート）で誰も持って
    いないものも消す。

## 22. ドキュメント・写真のプレビューを下へ引いて閉じる（iOS / Android、2026-10-12）

PDF や Office のファイルのプレビュー（全ページのビューア、PREVIEWS.md §5）を、写真と同じく下へ引いて閉じられるようにした
（利用者の要望：写真はスワイプで閉じるのにドキュメントは「閉じる」を押すしかなかった）。

### 22.1 どの引き方で閉じるか

- **ヘッダー（閉じる・名前・共有の帯）から下へ**：いつでも。
- **ページから下へ**：指を置いたときにページがいちばん上までスクロールしてあり、拡大していないときだけ。途中のページから
  下へ動かすのは今までどおり上へ戻るスクロールで、いちばん上に着いてもその指のまま閉じには変わらない（指を離して引き直す）。
  拡大中の下への動きはページを動かす（iOS）。上へ・横への動きは閉じない。ピンチの最中・直後（片方の指が残ったとき）も
  閉じない（iOS）。
- 引いている間は画面が指について下がり、後ろの会話が見えてくる（暗い幕が距離とともに薄れる。画面の半分で消える）。
- 指を離したとき：写真のビューアと同じ規則（iOS の `ViewerDismiss.shouldClose`）。下へ速く払う（900 pt/s・dp/s 超）か、
  画面の約 1/5（最大 140 pt・dp）を超えて引いていれば、そのまま下へ抜けて閉じる。上へ戻す動き（300 超）や短い引きはばねで
  元に戻る。iOS の「視差効果を減らす」では抜けずにその場で薄れて閉じる。
- 閉じる手段は残す：「閉じる」（iOS）／ ✕（Android）、Android の戻る（ジェスチャー・キー）、VoiceOver の
  エスケープ（2 本指の Z）、TalkBack の「閉じる」操作（`semantics { dismiss }`）。

### 22.2 実装

- iOS（`UI/DocumentPreviewView.swift`）：`DocumentPDFViewer` は自前のヘッダー（SwiftUI の `DragGesture`）と PDFKit の
  `PDFView` の上の 1 本指の `UIPanGestureRecognizer`（`DocumentPullController`）。PDFKit の中のスクロールビューの
  パンはこの引きが諦めるのを待つ（`require(toFail:)`、写真のビューアと同じ形）。始めてよいかは `DocumentDismiss.begins`
  （下向きが横より大きい・いちばん上・`scaleFactor` が `scaleFactorForSizeToFit` を超えていない）。移動は window の
  座標で測る（ビュー自体が指について動くので）。全画面のカバーは `presentationBackground(.clear)`。
- Android（`ui/DocumentPreview.kt`）：`PullToClose` がずれ（`graphicsLayer` の translationY）を持つ。ページの一覧は
  `NestedScrollConnection` で、一覧が使い残した下向きの指の動き（指を置いたときに一番上だった場合だけ。
  `awaitFirstDown` の Initial パスで `canScrollBackward` を見る）を引きに回し、引いている間の上向きの動きは一覧より先に
  引きを戻す。払いの速さは `onPreFling`。ヘッダーは `pullToCloseHandle`（指の位置を window の座標で測る。ヘッダー自体が指について動くので、`draggable` のローカルの座標では指の約半分しか動かなかった）。後ろの暗さはダイアログの window の `dimAmount`。
  規則は `DocumentDismiss`。Android のビューアにはピンチ拡大と横のページ送りが無い（PREVIEWS.md §5）。
- Quick Look（iOS の「開く」、元のファイル）はシステムのシートなので、もとから下へ引いて閉じられる。Android の
  写真のビューアも同じ引き方で閉じる（§22.4）。

### 22.3 試験

- iOS `DocumentPreviewTests`：`DocumentDismiss` の規則（向き・いちばん上・拡大・引きの量・離したときの判定）と、本物の
  `PDFView`（5 ページの生成した PDF を window に置く）で、いちばん上では始まり、スクロールした後と拡大中は始まらないこと。
- Android `DocumentPreviewTest`：一覧の前後で引きが取る量、閾値と払い、幕の薄れ。
- シミュレータ（iOS 26.5）とエミュレータ（ChikuwaChat_Pixel_9）で 6 ページの PDF：ページのスクロール、途中から下へ
  戻すスクロールで閉じないこと、いちばん上から引いて閉じる・短い引きは戻る、ヘッダーから引く、拡大中は閉じない（iOS）、
  戻るで閉じる（Android）。

### 22.4 Android の写真のビューア（2026-10-12）

ドキュメントと同じ引き方を Android の写真のビューア（`ui/ImageViewer.kt`。会話・送信前のタイル・キャンバスの写真）にも入れた
（iOS の写真のビューアはもとから下へ引いて閉じる）。

- **写真から下へ**：拡大していないとき、1 本指で下へ動かすと写真が指について下がり、後ろの会話が見えてくる（暗い幕が薄れる）。
  離したときの判定・ばね・抜け方は §22.1 と同じ（`DocumentDismiss.shouldClose`、`PullToClose`）。
- **何になるかは動き始めの向きで決める**（`ImageDismiss.decide`）：タッチスロップを超えた時点で、1 本指・拡大していない・下向きが
  横より大きいときだけ引き。横（斜め 45° ちょうどを含む）・上向き・2 本指（ピンチ、その後に 1 本残った場合も同じ動きの間は）・
  拡大中は今までどおりの拡大と移動で、その動きの間は引きに変わらない。拡大中に下へ動かすと写真を動かす。ダブルタップの拡大は
  今までどおり。
- **ヘッダー（✕・名前・他のアプリで開くの帯）から下へ**：いつでも（`pullToCloseHandle`）。
- 写真もヘッダーも指について動くので、引きの量と離したときの速さは window の座標で測る（ローカルの座標の差では指より遅れる）。
- ✕、戻る（ジェスチャー・キー）、TalkBack の「閉じる」操作（`semantics { dismiss }`）は残す。
- Android には 1 件のメッセージの写真を横にめくるギャラリーが無い（写真は 1 枚ずつ開く）。動画は別のビューア（`VideoViewer`、
  プラットフォームの `VideoView`）で開き、引いて閉じる操作はまだ無い（✕ と戻るで閉じる）。
- 試験：JUnit `ImageViewerTest`（`ImageDismiss.decide`：下向きの 1 本指は引き、横・45°・上・拡大中・2 本指は拡大と移動）。
  エミュレータ（ChikuwaChat_Pixel_9）で 600 × 900 の PNG：写真を 400 px 引くと画面が指について約 350 px 下がる（スロップの分だけ
  少ない）、閾値（140 dp）未満で離すと戻る、600 px 引いて離す・短く速く払うと閉じる、横の払い・上の払いでは閉じない、
  ダブルタップで拡大した後の速い下への払いは写真を動かすだけで閉じない、ヘッダーから引くと指についてくる、戻るで閉じる。
- 既知の点：ドキュメントのページの一覧から引くとき（§22.2 の `NestedScrollConnection`）は一覧のスクロールのローカルの座標の
  差なので、画面が指より遅れて下がる（エミュレータで 400 px の指に約 280 px）。閉じる・戻るの判定は正しく動く。

### 22.5 Android の写真のビューア：タップで帯を隠す（2026-10-27）

利用者の要望：写真だけを見たい。写真を 1 回タップすると、上の帯（✕・名前・他のアプリで開く）とシステムのバー（ステータスバー・
ナビゲーションバー）が消えて、黒い背景に写真だけになる。もう 1 回タップで戻る。会話・送信前のタイル・キャンバス・備品の
写真とドライブの写真（`DriveViewer` も `ImageViewer`）で同じ。

- 帯と背景（テーマの面の色 ⇄ 黒）は 180 ms で薄れる・現れる（`ImageChrome.FADE_MS`）。
- システムのバーは `WindowInsetsControllerCompat` で隠す（`BEHAVIOR_SHOW_TRANSIENT_BARS_BY_SWIPE`：端から払うと一時的に
  出る）。ビューアを閉じるとき（✕・戻る・下へ引く・TalkBack の「閉じる」）は必ず出し直す。
- 写真の大きさと位置が帯の出し入れで動かないよう、ダイアログは端から端まで（`decorFitsSystemWindows = false`、
  カメラの切り欠きの側にも広げる）にし、写真は画面いっぱい、帯は写真の上に重ねる（半透明の面の色、ステータスバーの分だけ
  下げる）。帯は今までどおり下へ引くと閉じる。
- 1 回のタップは `detectTapGestures` の `onTap`：ダブルタップの待ち時間を過ぎてから効くので、ダブルタップ（拡大・戻す）では
  帯は変わらない。ピンチ・拡大中の移動・下へ引いて閉じるは指の動きを使うので、タップにならない。Android の写真のビューアに
  横のページ送りは無い（§22.4）。
- TalkBack（タッチで探索）が有効な間は隠さない（タップは何もしない。隠れている間に TalkBack を入れると帯が戻る）。読み込み中と
  読み込めなかったとき（「再試行」）も隠さない（`ImageChrome.shown`）。
- 動画のビューア（`VideoViewer`）は変えない（タップはプラットフォームの再生コントロール）。
- 試験：JUnit `ImageViewerTest`（`ImageChrome` の切り替え・TalkBack・読み込み前）。

### 22.6 iOS の写真のビューア：タップでバーを隠す（2026-10-27）

利用者の要望。iOS の写真のビューア（`ImageViewer.swift`。会話の添付の写真と、ドライブの写真）で、写真を 1 回タップすると
上のバー（閉じる・ファイル名と「1 / 2」・共有）とステータスバー（ホームインジケータも）が消え、黒の上に写真だけになる。もう
1 回タップで戻る。0.2 秒のフェード（`ViewerChrome.fade`）。下のツールバーは無い。

- 1 回のタップは各ページの拡大のスクロールビューの `UITapGestureRecognizer` で、ダブルタップ（拡大）が失敗するのを待つ
  （`require(toFail:)`）。ダブルタップの拡大・ピンチ・拡大中の移動・横のページ送り・下へ引いて閉じるは今までどおりで、
  バーは出たり消えたりしない。消した状態はページを送っても続く（写真アプリと同じ）。
- VoiceOver が動いているときはバーを消さない（閉じる・共有に届くように）。消した状態で VoiceOver が入るとバーが戻る
  （`ViewerChrome.afterTap` / `whenVoiceOverChanges`）。消えている間のバーはタップも VoiceOver も受けない。
- 動画のビューア（`VideoViewer`）はシステムのプレイヤーのタップで自分のコントロールを出し入れするので変えていない。
- 試験：`ViewerDismissTests.testATapTogglesTheBarsExceptWithVoiceOver`、
  `ImagePagerControllerTests.testASingleTapOnAPhotoReachesTheViewer`。シミュレータ（iOS 26.5）で 2 枚の写真：タップで
  バーとステータスバーが消え、もう一度で戻る、ダブルタップで拡大・戻し（バーはそのまま）、横に送る、下へ払って閉じる。

### 22.7 動画のビューア：動画を画面全体の中央に（iOS / Android、2026-10-27）

利用者の報告：縦持ちで横長の動画を再生すると、上下の黒い帯の高さが揃わず、上が少し大きい。原因は両方とも同じで、動画を
「ステータスバーと上の帯（閉じる・名前・共有）の下から、画面の下まで」の領域の中央に置いていたこと（iOS はさらにホーム
インジケータの分を含め、Android はナビゲーションバーの分を除いていた）。帯の高さの分だけ動画が下へずれていた。

- 動画は画面全体（セーフエリア・システムのバーを含む）の中央に置き、上の帯はその上に重ねる（帯はステータスバーの下、
  横は切り欠きを避ける）。帯の下は動画の外の黒なので、横長の動画を縦持ちで見る限り帯と動画は重ならない。
- iOS（`VideoViewer.swift`）：`VideoPlayerPage`（`AVPlayerViewController`）を `ZStack` の下に置いて
  `.ignoresSafeArea()`、帯を上に重ねる。プレイヤー自身のコントロールが帯の下に隠れないよう、プレイヤーの
  `additionalSafeAreaInsets.top` を帯の高さ（44 pt）にする（動画の位置はセーフエリアに左右されず、ビュー全体の中央のまま）。
- Android（`ui/VideoViewer.kt`）：ダイアログを端から端まで（`decorFitsSystemWindows = false`、切り欠きの側にも
  広げる。写真のビューア §22.5 と同じ）にし、動画は画面いっぱいの `Box` の中央、帯はその上に重ねて
  `WindowInsets.safeDrawing` の上と左右だけ空ける。黒の上なのでシステムのバーのアイコンは白。再生コントロール
  （`MediaController`）は今までどおり動画の下端に付く。読み込めなかったときの表示は `safeDrawingPadding` の内側。
- 測った値（縦持ち、16:9 の動画）：
  - iOS シミュレータ（iPhone 17 Pro、402 × 874 pt、セーフエリア上 62・下 34）：前は動画の上の黒 377 pt・下 271 pt
    （差 106 = 62 + 44）、後は 324 pt・324 pt（スクリーンショットで 972 px・972 px）。
  - Android エミュレータ（ChikuwaChat_Pixel_9、1080 × 2424 px）：前は上 1011 px・下 806 px、後は 908 px・909 px。
- 試験：`M38Tests.testALandscapeVideoIsCentredOnTheWholeScreen`（生成した 320 × 180 の動画を `VideoViewer` で
  window に置き、`AVPlayerViewController.videoBounds` の上下の余白が等しいこと、プレイヤーのセーフエリアの上が
  帯の下まであること）。Android は配置だけの変更で、エミュレータで測った（✕ で閉じる、タップで再生コントロールが
  動画の下端に出ることも見た）。

## 23. メンションの候補の並び（4 クライアント、2026-10-21）

利用者の要望：入力欄で `@` を打つと、ワークスペースの全員がユーザー名の順に並ぶだけで、話している相手がなかなか出てこない。
今の会話にいる人とそのチャンネルに入っている人を先に出す。サーバの API は変えず、端末が持っている物（読み込んだ
メッセージ、DM の参加者）と、今ある `GET /channels/{id}/members` で読んだメンバーで決める。規則は 3 端末で同じで、`apps/shared/mention-rank.json` を 3 端末の試験が読む。

- **絞り込みは今までどおり**：ユーザー名が打った語で始まる人、または表示名が打った語を含む人（大文字小文字を区別しない）。
  無効化した人と AI 以外のボットは出さない（AI.md §2.1）。
- **人の並び**（上ほど先）：
  1. **一致の仕方**（語を打ったときだけ）：ユーザー名か表示名が語で**始まる**人が先、途中に含むだけの人は後。
     ユーザーに読み（かな）の欄は無いので、ユーザー名と表示名だけで判断する。
  2. **段**：
     - (a) **この会話で最近書いた人**、新しい順。スレッドではスレッドの書き手（親と返信、新しい返信の人から）が先で、
       その後にチャンネルの書き手。チャンネルでは読み込んである時系列の書き手。数えるのはそれぞれ新しい
       **50 件**まで（削除したメッセージ・`type = system` の行は数えない）。
     - (b) **会話のメンバー**で (a) にいない人。DM・グループ DM は参加者（`ChannelOut.dm_user_ids`）、公開・非公開
       チャンネル（とそのスレッド）は下の「チャンネルのメンバー」。
     - (c) それ以外の全員。
     - (d) **自分**は（最近書いていても）いちばん後。
  3. 同じ段の中は**表示名**（日本語の照合順。Desktop / Web は `Intl.Collator("ja")`、iOS は `compare(_:locale:)`、Android は
     `Collator.getInstance(Locale.JAPANESE)`）、同じならユーザー名（コードポイント順）。
- **グループ（`@m1` など）と `@channel` / `@here`** は今までどおり人の後（グループは名前順、その後に `@channel`、`@here`）。
  何も打っていないときも人が先。
- **出す数**は 6 → **8**。Desktop / Web の入力欄の一覧（1 行約 32 px、絵文字の候補も同じ場所に 8 件出している）、iOS と
  Android の横に流れる候補の列のどちらにも収まる。キャンバス・ドキュメントの編集は前から 8。
- **キャンバス・ドキュメント**：会話が無いので (a) は無い。キャンバスはそのチャンネルのメンバー（DM は参加者）を (b) に
  し、自分は最後。ドキュメント
  （Wiki のページ）はチャンネルに属さないので (c) と (d) だけ。スマホのドキュメントの見たまま編集（同梱のエディタ、
  WIKI.md §30）はネイティブが自分の id を渡さないので、表示名の順だけ（自分も他の人と同じ段）。

**チャンネルのメンバー**：公開・非公開チャンネルで `@` の候補が初めて開いたとき（入力欄・スレッドの入力欄・キャンバスの
編集）、`GET /channels/{id}/members`（ページ分けなし、研究室なら数十人）でメンバーの id を読み、端末のメモリにだけ持つ
（保存しない。サインアウト・ワークスペースの切り替えで消える）。候補は待たずに出し、届いたら並べ直す。
- 読み直すのは、メンバーが変わったと分かったとき（`channel.member_added` / `_removed` / `_updated` で会話ごとの番号が進む。
  開いているメンバーの一覧も読み直す）と、前に読んでから 5 分たった後に候補が開いたとき（落とした WebSocket のイベントの

- 読めなかったとき（オフライン・権限など）は今までの物（無ければ (b) なしの並び）のままで、候補は止めない。知らせは出さない
  （Desktop / Web はコンソールに警告）。30 秒たつまでは読み直さない。
- DM・グループ DM は `dm_user_ids` があるので読まない。

スレッドの返信は、スレッドを開いて読み込んだ分だけ数える。

### 26.2 変えたこと

- **分割が要る幅**（`MainLayout.of(sizeClass, width:)`、`MainLayout.splitMinWidth` = 700 pt）：regular でも窓が 700 pt より狭ければ電話の形。
  内側を縦長に持つと 669 pt で regular のまま、分割はサイドバー（320）で会話が 350 pt ほどしか残らず、そのうえ UIKit の分割のレイアウト
  （`UISplitViewController` の panel の solver）が止まらずアプリが固まった（CPU 100%、`sample` で確かめた）。iPad mini の縦（744）は
  分割のまま。窓の幅はシーンのウィンドウから最初の描画の前に読み、幅が変わるたびに見直す（サイズクラスが変わらずに 700 を越える）。
- **形が変わっても画面の中の状態を失わない**（`UI/LayoutCarry.swift`）：開いている会話・スレッド・ドライブのフォルダ・下書きは前から
  残る（§13.2）。折りたたむ・開くたびに分割 ⇄ 電話の形が替わり、会話のビューが作り直されて、一覧の位置・キーボード・会話の上のシートが
  消えていた。会話（`ChannelView`）とスレッド（`ThreadView`）が自分の状態を書き（`ConversationCarrier`）、形が替わる直前に MainView が
  前の会話とスレッドの分を渡し（`layoutChanging`）、新しい形のビューが現れるときに受け取る（5 秒以内、使い切らない：新しい形のビューは
  落ち着くまでに 2 回作られることがある）。
  - 一覧の位置：一覧が保っている行（`keptRowId`、ID でスクロール。上下逆の一覧なので画面の下の行）。新着の位置への着地はしない。
  - キーボード：入力欄が持っていた（形の変更そのものが先にキーボードを下げるので、1.5 秒以内に失ったものも持っていたとみなす）。
    `composerFocus` で入力欄に戻す（スレッドの入力欄にも広げた）。
  - 会話のタブ（キャンバス・タスク・ドライブ…）と、ドライブのタブで開いていたフォルダ、チャンネルの詳細（積んだ画面）。
  - メッセージのシート（長押しの操作・リアクションなど）と会話のシート（リンク・メンバーの追加）は、新しい画面が落ち着いてから（0.6 秒）
    出し直す。

## 27. テーマの色・真っ黒のダーク・ワークスペースごとの色（2026-10-27）

Desktop の「テーマの色」（apps/desktop/README.md「表示：配色と文字の大きさ」）をスマホにも持ってくる。色の値は
`apps/shared/palettes.json`（6 色、並びは設定の順、先頭が既定）が元で、Desktop の `tests/palettes.test.ts` が app.css と、各

### 27.1 Android

- **テーマの色**：Taylis（栗、既定）・藍・緑・紫・紅・グレー（名前は Desktop の `theme.palette.*` と同じ、日本語・英語・中国語）。
  `ui/ThemeColors.kt` の `PaletteColors` が JSON の `accent`・`accent-solid`・`accent-soft` を持ち、`ThemeColorsTest` が JSON と
  比べる（`sidebar` はスマホでは使わない）。それまでの #5b5bd6 の配色（M40）はやめ、既定は Taylis になる。端末の壁紙の色
  （Material You）はアプリでは前から使っていないので、「端末の色」は足さない（ホーム画面のウィジェットは Android 12 から壁紙の
  色のまま、それより前は既定のパレット）。
- **Material 3 の役への割り当て**（`ThemeColors.roles`）：
  - ライト：`primary` = `accent`（リンク・アイコン・スイッチ・送信ボタン）、その上は白（`accent` = `accent-solid`）。
    `primaryContainer` は白に `accent` を 16 % 混ぜた淡い色（FAB・自分のリアクション）、`secondaryContainer`（選択中の行・
    タブの印）は `accent-soft` に `accent` を 8 % 混ぜた色（`accent-soft` のままでは地の色とほぼ見分けられない）。
  - ダーク：`primary` = 文字用の明るい `accent` で、その上の文字は `accent` を暗くした色。`primaryContainer` = `accent-solid`
    で、その上は白。`secondaryContainer` = `accent-soft`。M3 のダークの決まり（明るい primary に暗い文字、塗りは
    container）に合わせたので、送信ボタンなど `primary` の塗りは Desktop（ダークでも `accent-solid` に白）と違い明るい色になる。
  - 地の色・文字・線（surface 系・outline）はグレーにアクセントを数 % 混ぜた色。エラーの赤・tertiary（オレンジ）・在室や
    プレゼンスの色はパレットで変えない。
  - `ThemeColorsTest` が 6 色 × ライト・ダーク・真っ黒で、文字の組（onPrimary / primary、onSurface / 各 container、リンクの
    primary / surface など）の 4.5：1 と、primary・outline の 3：1 を確かめる。
- **ダークを真っ黒にする**：「表示」の「端末に合わせる / ライト / ダーク」の下のスイッチ（初期値オフ）。ダークで表示している
  とき（端末のダークも）だけ効く。`background`・`surface`・`surfaceDim`・`surfaceContainerLowest` が #000 になり、
  `surfaceContainerLow`（ボトムシート）→ `surfaceContainer`（下のタブ）→ `High`（ホームのタイル・ダイアログなど）→
  `Highest` → `surfaceBright` がごく暗いグレー（#101010〜#303030 にアクセントを少し）で一段ずつ明るくなり、黒の地から
  離れて見える。上のバーと一覧・会話の地は黒のまま（入力欄は線で囲む）。アクセントと文字の色はダークと同じ。ステータスバーとナビゲーションバーは edge-to-edge で透けているので
  地の黒がそのまま見え、アイコンはダークの色。ウィンドウの背景（画面の切り替えやキーボードの動きの間に見える）も
  `background` に合わせる。
- **ワークスペースごとの色**：ワークスペースが 2 つ以上のとき、テーマの色の上に「このワークスペースだけ」/「すべての
  ワークスペース」（Desktop の `ThemeScope`）。「このワークスペースだけ」で選んだ色はそのワークスペースのもの、無いワーク
  スペースは「すべて」の色。「すべてのワークスペース」に切り替えると画面の色が共通になり、各ワークスペースの色は消える
  （Desktop と同じ）。ワークスペースを切り替えるとすぐ色が変わる（`AppController.palette` が `activeKey` から読む）。
  「ワークスペースを追加」のログイン画面（開いているものが無い）では共通の色。
- **保存**（SharedPreferences、`ThemePrefs`）：`theme.palette`（共通。既定なら無し）、`theme.palette.workspaces`（JSON、キーは
  ワークスペースの一覧のキー＝サーバの URL）、`theme.black`（"on"、オフなら無し）。読めない値は既定。
- **設定の画面**：テーマの色はアクセントの丸（選んだものにチェックと枠）と名前。「自分」の一覧の「表示」の行の右には
  「Taylis（栗）」、端末に合わせないときは「Taylis（栗）・ダーク」のように出す。
- **確かめたこと**：`./gradlew :app:testDebugUnitTest :app:lintDebug :app:assembleDebug`。エミュレータ（API 36）で Taylis と藍のダーク・
  真っ黒、緑と Taylis のライト（ホーム・会話・入力欄・ボトムシート・ダイアログ・設定）、「このワークスペースだけ」で選んだ紫が

  「キャンセル」、右上の赤い「削除」）。「ドライブの 2 件のファイルもゴミ箱に移す」のスイッチと説明の 1 行。

  付いたファイルの行は日時の前に小さな吹き出し。詳細に「投稿」の節（「三井 · 日時 · #ch（スレッド）」と「メッセージを表示」）。
